против живой сети, сборка — в Docker `rust:1.96-bookworm` на n4, раздача через

Топология: n1 = sg (10.10.99.2), n2 = uk (10.10.99.3), n3 = ca (10.10.99.4),
n4 = ge (10.10.99.5). Активный сет — три валидатора: `0xb49F08B2…`,

## 1. Follower: эпоха из наблюдаемых границ

**Было.** Нода в режиме `--upstream` доходила до 223122 и вставала навсегда.
Блок 223123 запрашивался и доставлялся бесконечно (1620 запросов / 3240
доставок) и каждый раз отвергался marshal'ом без единой строки о причине.

**Причина.** `FollowerEpocher::containing` считал эпоху формулой `(h−1)/L`.
Границы эпох не лежат на сетке: номер эпохи — счётчик (`epoch + 1`), а высота
активации — накопитель (`planned = last_activation + L`,
`last = max(observed, planned)`) плюс окно допуска в 600 блоков. По цепи через
`outbe_getFinalization`: 222001 → 185, 223122 → 185, **223123 → 186**, 224400 →
186. Формула ждала 186 на 223201 — расхождение 78 блоков. Marshal сверяет
`finalization.epoch() == bounds.epoch()` и на несовпадении делает
`send_lossy(true)`, то есть молча выбрасывает доставку.

**Стало.**
- `follow/epocher.rs` — карта наблюдаемых границ (`BTreeMap<height, epoch>`)
  вместо формулы. `record()` идемпотентен и понижает записанную высоту, если
  пришла меньшая для той же эпохи.
- `follow/resolver.rs` — граница записывается в карту **до** `handler.deliver`,
  в том же последовательном таске.
- `follow/engine.rs` — `bootstrap_anchor` идёт вниз по локальной истории через
  `parent_digest()` до носителя действующей эпохи. Ловушка: первым при обходе
  встречается `CommitteePreAnnounce{E+1}`; зарегистрировать его — значит поднять
  `highest_registered` и защитой D1 отвергнуть саму E. Регистрируется только
  носитель нужной эпохи. Потолок обхода — `epoch_length + activation_grace` из
  `DkgRotationParams::from_genesis`.
- `follow/driver.rs` — предрегистрация эпох снесена целиком (−170 строк).

12 тестов, писались до кода. Проверено на живой сети: n1 прошёл 223123 и
догнал сеть.

**Годится для main.**

## 2. Vote: досрочная финализация по кворуму

`process_begin_block` читает набор валидаторов и считает tally один раз на блок
и финализирует пропозал при `deadline_passed || quorum_reached`.
`finalize_voting` получает `tally` и `active_count` параметрами — второго
прохода по `proposal_voters` нет.

Проверено на цепи: пропозал #1 (USD777) стал `Approved` за ~86 тысяч блоков до
дедлайна, токен создан по `0x53c043b12DeCAd309B4cFcbb23849a1940334473`, бонд
вернулся.

**Гейт по высоте — обязателен.** Хронология:

```
234281  пропозал создан, бонд заэскроуен
234600  голос 1
234610  голос 2   ← кворум 2 из 3
234614  голос 3
235507  финализирован — первый блок, собранный новым бинарём
```

Блоки 234281…235506 собраны по старому правилу. Нода, переигрывающая их новым
бинарём, одобряет пропозал на 234611 и умирает на `receipt root mismatch`
(`got 0xb1e296a6…`, `expected 0xcb4e51ff…`). Гейт:
`chain_id != 54322345 || block_number >= 235507`.

**Годится для main**, но гейт там нужен по форку, а не по константе высоты.

## 4. OCOMP lifecycle не роняет блок

`run_lifecycle_begin` выполняется под чекпойнтом; при ошибке — `tracing::error!`
с причиной, откат, и день, чей FSM не восстанавливается, закрывается: бюджет
уходит в carry-over `PromisLimit`, день помечается `FAILED`, FSM чистится. Блок
продолжается.

**Для main границу надо сузить.** Сейчас глушится любая ошибка, включая «сторидж
вернул мусор». Уводить в `FAILED` следует только несогласованность самого дня,
сбои хранилища оставить фаталом.

## 5. Почему OCOMP не досчитал ни одного дня

Главное за сессию открытие, и оно не про конфигурацию.

Открыть снапшот можно, только когда глобальный маркер CE-дерева стоит **ровно**
на блоке джобы (`snapshot_control.rs:155`). Маркер двигает `ExecutorActor`
(`executor/actor.rs:850`) сразу при канонизации блока. Пины промоутит и
вооружает другой актор — `FinalizationActor` кладёт блок в очередь, а рабочий
поток `retention.rs:867` разбирает её через `spawn_blocking` с построением
MPT-пруфа, проверкой заголовка и fsync журнала.

То есть окно — это гонка между лёгким исполнительным актором и тяжёлым
ретеншен-воркером, и тяжёлый проигрывает всегда. По логу он отстаёт стабильно на
21–22 блока. Успешных вооружений — **ноль за всё время жизни сети**. Джоба
создаётся каждый блок, окно живёт один блок; константами это не лечится.

Партиционирование по дню при этом есть — `PartitionRef::TributeWwd(day)` даёт
дню свой `CollectionKey`, интент вмораживает `sealed_tribute_collection_key` и
`sealed_tribute_collection_root`, а `repository.rs:88` прямо называет партицию
дня immutable. Но `finalized_marker()` — это `db.marker()`, один глобальный
маркер всего дерева: дерево одно, in-place, версий нет, и каждый блок в него
пишутся новые трибьюты. Поэтому сравнивается состояние всего дерева на
конкретной высоте, а не тот корень, который интент уже заморозил.

**Правильное лечение:** проверять корень запечатанной коллекции вместо
глобального маркера. Данные для этого есть — `completed_partition_root`
считается на границе блока. API корня по коллекции в `tree_manager` надо
добавить.

**Что сделано в testnet3:** проверка снята целиком (и сравнение, и вариант
ошибки `CeMarkerMismatch`). Снапшот вооружается на текущем маркере. Побочный
эффект: каждая нода вооружается на своём маркере, и результаты совпадут только
если день действительно неизменен как партиция. Код это утверждает, экспериментом
не подтверждено.

**В main не переносить.**

## 6. Комитет результата

`POC_COMMITTEE_SIZE = 4`, `POC_COMMITTEE_THRESHOLD = 3`. Кворум считается по
константе (`vote.rs:383,464,507`), поле `threshold` в снапшоте только сверяется
на равенство при установке.

Значит одной работающей ноды не хватит никогда. Индексы 0..3 — n1..n4, n1 из
активного сета выпал, запас нулевой.

В testnet3 порог опущен до 2; поле снапшота осталось 3 под отдельной константой
`POC_COMMITTEE_SNAPSHOT_THRESHOLD`, иначе комитет из генезиса перестал бы
валидироваться.

Проверено попутно: `key_epoch` и `allowed_purpose_bitmap` участников заведомо
корректны — `validate_semantics` не пропустила бы комитет при установке. Нижняя
граница окна валидности тоже проверяется при установке (`fork.rs:90`). Верхняя
граница без декодирования стораджа не читается; первая поданная подпись покажет.

## 7. Прочие правки

- `RESULT_DEADLINE_BLOCKS` 64 → 640, одновременно в исполнении
  (`metadosis/ocomp/expiry.rs`) и в ретеншене ноды (`stack.rs:3580`) — иначе пин
  освобождается раньше, чем истекает дедлайн джобы, который он защищает.
- `max_pending_jobs`: пробовал поднять до 255, откатил — упирается в
  `MAX_LIVE_JOBS = 2` в схеме metadosis, см. остановку №6.
- `eprintln!` → `tracing::warn!` в `node/src/ocomp/control.rs:284`. Это был
  единственный `eprintln!` во всём `node`/`engine`/`consensus`; из-за него все
  отказы контрольных сессий уходили в stderr мимо логов.
- uid-изоляция вырезана из `outbe-ocomp` целиком: `PeerCredentials`, обе
  реализации `peer_credentials`, `expected_peer_uid`/`expected_server_uid`,
  ошибки `UnauthorizedPeer`/`EffectiveUidUnavailable`/`UnknownUser`/
  `EffectiveUserMismatch`, `effective_uid`/`uid_for_user`/`effective_user_name`/
  `require_effective_*`, флаги `--ocomp.supervisor-uid` и
  `--ocomp.snapshot-exporter-uid`, проверки владельца файла ключа и sign-once
  журнала. 20 файлов, `local_control.rs` −164 строки.
- `testnet_ocomp_force.rs` — форс-включение профилей OCOMP на высоте 221200 для
  chain 54322345: цепь стартовала без protocol-v1, `ocomp_profile_ready` остался
  `false`, и каждый терминальный запрос молча откладывался. Штатно догнать
  нельзя: обработчик активации отвергает цепь с живой эмиссией. **В main не
  переносить**, но причина там существует — нужен нормальный путь включения на
  живой сети.

## 8. Эксплуатация

Пути к артефактам OCOMP вшиты в бинарь константами, и в деплое они пропатчены
под `/opt/outbe-chain`. Синхронизируя свою версию `main.rs`, я затёр этот патч —
supervisor и exporter стали открывать `/etc/outbe/ocomp/protocol-bundle-v1.ocb1`,
которого нет, и падали с `Permission denied` (EACCES вместо ENOENT, потому что
`/etc/outbe` — `0750 root:root`). Пути возвращены в `bin/outbe-ocomp/src/main.rs`,
13 констант.

`ocomp.sh` на n4 переведён на одну учётку: `SUPERVISOR_USER`, `EXPORTER_USER`,
`WORKER_USER` и обе группы указывают на `NODE_USER` (`ubuntu`), плюс
`chown -R ubuntu:ubuntu /opt/outbe-chain/ocomp/data`. До этого CAS-каталог
создавал supervisor, а exporter под другим пользователем не мог сделать
`chmod 0770` чужого каталога и падал с EPERM (`cas.rs:520` жмёт права
безусловно). Бэкап — `ocomp.sh.bak-uidsplit`. На n1–n3 скрипт не менялся.

Разложено в `/shared/testnet3-votegate/`:

```
outbe-chain  6c1e40e754e4931f
outbe-ocomp  554d48fcffc31f59
ocomp.sh     c43cf960965ddd29
```

Три изменённых числа (порог, дедлайн, приём джоб) консенсусно видимы и гейта не
имеют: ноды на разных бинарях разойдутся, перезапускать надо вместе.

## 9. Открытые дефекты, кода нет

1. **Нода не поднимает контрольные сокеты после нечистой остановки.**
   `bind_control_socket` (`node/src/ocomp/service.rs:126`) отказывается биндить,
   если файл уже существует, а свои сокеты при остановке нода не удаляет. Одна
   нечистая остановка — и OCOMP не подключится никогда, ошибка только в логе.
   Лечится удалением файлов вручную. Чинить: удалять свой сокет на старте, если
   он не занят.
2. **Exporter не может пройти recovery.** Стадия `recover node export commit`
   получает от ноды `snapshot handoff was not found` (нода после рестарта про
   prepared-экспорт не знает), считает это ошибкой стадии, ретраится и выходит.
   На n4 один такой зависший экспорт (`463118ee…`) отнесён в
   `exporter-v1.stale-*`. Чинить: «нечего восстанавливать» — не ошибка.
3. **`run_startup_live_join_reshare` — дедлок** (`stack.rs:6312`). Цикл читает
   собственную высоту исполнения, а marshal стартует после цикла, так что голова
   не двигается. Ниже `freeze_height` — ждёт вечно, выше `activation_deadline` —
   падает. Валидатором такую ноду поднять можно только случайно попав в окно.
4. **`MAX_LIVE_JOBS = 2`** — жёсткий предел схемы (индекс планировщика, окна
   ответов). Любой приём выше него делает терминальную системную транзакцию
   фатальной.
5. **`MAX_TRACKED_JOBS = 256`** против протокольных 730 (365 × 2 живых дня).
6. **Якорь активации эпохи — процесс-локальный,** ноды могут разойтись в том,
   где следующая граница.
7. **e2e ничего из этого не ловит:** минуты вместо суток, идеальная сеть без
   дрейфа активации, один uid на все роли.
