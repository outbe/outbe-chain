## Required fix

### R3-R3-F1 — high: stable membership does not give a long enough material generation for the one-attestation carrier

`design.md:266–276` allows one identity attestation per block. A checkpoint requires q participants (`257–263`); jobs use the current epoch/material, and a material change clears pending slots (`297–305`). New jobs require authenticated current-material binding (`216–225`, Review/Merge anchor at `278–285`). The liveness condition at `349–351` names eventual stable committee/delivery, without a minimum current-generation window or another publication mechanism.

Actual runtime rotates even when membership is unchanged: `engine/src/stack/epoch/ceremony.rs:36–48` schedules by freeze height; `epoch/ceremony/freeze.rs:48–75` calculates `is_validator_set_change` but still launches the ceremony; `stack/dkg/persistence.rs:259–271` increments epoch/material regardless of that boolean; `epoch/activation.rs:117–129,218–229` activates the new material and advances epoch. `stack/dkg/handoff.rs:30–36` derives the next planned activation from last activation + epochLengthBlocks. Thus a stable participant list does not freeze the epoch/polynomial/version. Source current default epoch length is 300 (`scripts/genesis_network.py:41`), and seeding only requires it to be positive (`scripts/genesis_seed_validators.py:189–193`).

At supported n=256, q=171. If each new material generation requires its own q-attestation BindMaterial before Review, even ideal delivery/no finality or Git delay needs at least 342 blocks; a 300-block generation leaves only 129/171 Review attestations. The next material transition invalidates those slots; repeating the same schedule never publishes a Review. This is a necessary slot-count counterexample, not a production runtime execution claim. It is reproduced by `R3-artifacts/epoch-window-check.py` / `.log` for five generations, with perfect delivery and every block available. Actual DKG/mandatory artifacts would reduce carrier availability further.

The default DKG prepare window of 30 alone does not establish that n=256 can actually rotate exactly every 300 blocks, so I do not claim a reproduced default-node deadlock. A supported `epochLengthBlocks=300, dkgPrepareWindowBlocks=200` permits the q dealer logs to be finalized before planned activation; `DkgRotationParams::from_genesis` accepts that window and clamps it to the epoch length (`handoff.rs:11–26`). Timely periodic activation is therefore an admissible source schedule, rather than something stable membership disables. Source SDK `Info::required_commitments` uses the dealer/prior quorum; even those q logs fit this configured preparation window.

The text explicitly says BindMaterial after membership transitions, but does not define an alternate current-material binding path on same-membership numeric epoch/material transitions. If the intent is to skip the q checkpoint on those transitions using the already chain-authenticated DKG output, the contract must state and prove that rule, including how current body/anchor/material commitments and historical bindings are selected. Silently reusing an old material binding is not the currently specified exact-current-generation check. Even a skip rule needs a minimum sufficient current-generation window for a q-attestation Review and Merge checkpoint under allowed short epochs; merely stable membership/eventual delivery is not that window assumption.

Required: choose a concrete bounded publication/epoch-window rule, such as a bounded aggregate current-set certificate carrier or an enforced sufficient generation window plus defined binding reuse/progress semantics and delivery assumptions. Preserve old-material/current-set rejection, n=256 bounds, mandatory artifact reservations and nonblocking consensus. Add a finite scheduling scenario with stable membership but repeated material versions, maximum q, allowed short/default epochs, BindMaterial→Review→Merge and transition/reset; map the production cadence tests to P3/P6/P8. Do not merely waive n=256 or treat periodic reshare as optional churn.
