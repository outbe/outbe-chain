## Detailed requirements and negative review

- **Canonical exact subject:** V1 JSON has a single byte representation. Decode is bounded at512 bytes and compares re-encoding with input. Fixed20-byte nonzero OIDs prevent alternate lengths/zero subjects. Unknown/duplicate fields, extra whitespace, uppercase OID spelling, version2, numeric alternate version, other branch/action and oversized payload reject. Revision changes produce different bytes. Admission checks repository existence in the owning registry; it does not fabricate Git existence proof.
- **Authority and immutable decision:** Only the production registry can dispatch the target through Vote. The approved callback checks the stored proposal target, payload, proposer, deadline and status, then preserves an existing matching approval. It introduces no user delegation, Ed authority substitution, revocation endpoint or accepted-patch cancellation. Native BLS network authority remains a separate signing requirement. Tests that call internal Rust handlers directly are negative/replay probes, not the sole lifecycle proof; the actual EVM fixture exercises the external path.
- **Decision versus execution:** The immutable row contains payload, terminal height and timestamp. Stage1 means execution Pending, not Review published or Merge complete. No execution setter or offchain side effect was introduced. Same proposal replay leaves the original permission unchanged. Different proposals remain distinct decisions.
- **Current membership:** `validatorset/runtime/queries.rs:129` uses `ValidatorLifecycle::is_current_consensus_participant`; adapter.rs distinguishes Active, Exiting, JailRetained and Pending phases. The new predicate then selects ACTIVE. A retained jailed signer cannot vote or inflate the denominator. Cast, read and terminal tally deliberately re-evaluate the current list. Membership changes after terminal acceptance do not revoke the immutable permission.
- **Rollback and errors:** Proposal write, electorate write, reserve and event occur in the existing admission checkpoint. Terminal approval creation/stage write, Vote status, settlement and logs use existing nested checkpoints. Infrastructure/storage errors propagate as errors; target-declared execution Error uses the existing rollback/refund path. The changed target does not convert failed terminal execution into permission. Full suites exercise existing target error and bond semantics as well as the new mutation-by-mutation failure fixture.
- **Finality:** The onchain ABI getter is a view of decision state; it is not by itself an offchain finality assertion. The new consumer API requires a canonical finalized source block and uses `state_by_block_hash`, checks the provider's canonical finalized hash, and preserves the returned source block. Distinct hash-backed fixture states and panic-on-fallback APIs test this distinction. Provider errors are propagated, never replaced with latest state. No current electorate recheck revokes an already accepted historical permission.
- **Bounded work and compatibility:** The target payload and record are bounded; there is no Radicle lookup in consensus. At n256/171 Yes the independently rerun storage-meter fixture reports max cast1,121,500 and terminal1,228,600 gas, below its2M/5M assertions. This measures the production-shaped storage meter, not a256-node network or a full cold-state EVM benchmark. Existing ABI/routes/seeded slots remain stable; new slots are appended. Other targets retain stored/default Active behavior, with their full regressions green. No new network format/signing algorithm is claimed by P5.
