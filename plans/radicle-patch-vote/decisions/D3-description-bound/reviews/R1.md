## Contract/scope and compatibility

A correct A changes the accepted governments genesis input range, not BLS/Vote logic. Set the description maximum to 255 bytes and descriptor maximum to `97+255=352`; preserve OGD1 version, order and every byte for valid 0..255-byte inputs. Keeping the u16 length field is correct; changing framing is unnecessary. Reject longer values before committing seeding state or starting materialization. Never truncate, normalize or silently substitute description bytes, because those bytes contribute to descriptor/identity/RID commitments.

This is a real compatibility change for 256..1024-byte inputs. An already-seeded chain with such a description can be accepted by old code and rejected by corrected code, including the registry's bounded descriptor reader (`crates/system/radicleregistry/src/runtime.rs:29–59`). User approval must not be presented as permission to rewrite an existing genesis. I did not inspect deployments; whether any affected genesis exists remains unknown. For descriptions at most 255 bytes, encoding/hash stability follows directly from the unchanged encoder framing, but must also be covered by retained frozen vectors after implementation.

Retaining 1024 would require changing the native constructor **and** native reader acceptance, with a separate compatibility assessment. A does not authorize that larger alternative. Heartwood's shared native/Ed rules remain untouched.
