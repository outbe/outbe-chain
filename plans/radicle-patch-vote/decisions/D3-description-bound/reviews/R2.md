## Scope and compatibility

A changes the upper bound only. Fixed OGD1 overhead is 97 bytes, so the new total cap is 352. For descriptions <=255 bytes, unchanged field layout/version and literal bytes imply unchanged OGD1 bytes/hash and downstream identity inputs. A must not truncate descriptions, normalize Unicode, move data to another field, change schema version merely to hide the correction, or widen native Project acceptance. Native Ed25519 behavior remains the same.

Descriptions in 256..1024 were previously valid genesis inputs and become invalid. This is an externally visible compatibility restriction. It reaches more than genesis preparation: registry descriptor decoding, engine startup, and consensus genesis activation all consume the bounded codec (`crates/system/radicleregistry/src/runtime.rs:29-59`; `crates/blockchain/engine/src/stack/startup.rs:3-30`; `crates/blockchain/node/src/consensus/policy.rs:43-64`). Existing seeded chains in that range could therefore refuse startup/block validation after an upgrade. I did not inspect deployments, and this review does not authorize rewriting any genesis or changing a running network. If such a deployment is identified, its compatibility decision remains separate and must not be silently treated as solved by this proposal.

The alternative of keeping 1024 would require an intentional native schema change, including constructor and deserializer acceptance and legacy-reader compatibility. That is not required to establish the present defect and is not an approved fallback. I did not investigate unrelated D1/D2, fetch/storage redesign, signing algorithms, or new policy threats.
