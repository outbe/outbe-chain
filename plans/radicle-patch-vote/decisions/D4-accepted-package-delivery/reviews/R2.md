## Two necessary proposal corrections

1. **Define how archive traffic shares channel 8 without starving endpoint/OSIG traffic.** Proposal lines85–92 name quota32 messages/s, a256 pending cap, queues and a requirement not to block signatures, but specify no pacing/admission/priority mechanism. Existing quota is per peer and shared by every message on channel8 (`crates/blockchain/consensus/src/config.rs:35–37`, registered once in `engine/src/stack/epoch/transport.rs:144–149`). The endpoint, OSIG and archive paths therefore cannot each assume32 messages/s. Even honest bulk transfer can consume the common allowance before a signing contribution is sent; distinct inbox keys alone do not solve this. The existing actor also has one256-command mailbox (`integration/network.rs:236`). Specify bounded low-priority archive request/response work with a conservative share of the common quota, endpoint/OSIG-first sending, retry/backoff after rate limitation, and separate archive pending/inbox accounting so an archive backlog cannot fill signing command capacity. The precise internal constants are an implementation choice; no new channel, configurable protocol or peer-admission redesign is requested. State the guarantee as bounded non-starvation under the existing transport assumptions, rather than immunity to arbitrary admitted-peer flooding. Add the coexistence test to the listed proof: pending large archive while real endpoint/OSIG traffic continues and archive subsequently resumes.

2. **Name the effective byte budget and what it counts.** Proposal lines88–91 say “existing native data-fetch limit”, but two different real limits exist: `radicle-fetch/src/state.rs:25–30,108–114` defaults special refs to5MiB and data refs to5GiB, while `radicle/src/node/config.rs:138,150–170` defines configured `limits.fetch_pack_receive` (default500MiB), actually applied to incoming streams by `radicle-node/src/wire.rs:784–791`. Select a precise existing effective value, preferably no greater than the configured receive limit and relevant fetch-data limit. Specify aggregate accounting for metadata plus closure object bytes, duplicates/retries and temporary disk occupancy per active import; bound concurrent imports rather than multiplying a whole-repository budget by256 outstanding chunks. Offset/length arithmetic must be checked before allocation/write, with cleanup on rejection/interruption. Existing `review::object_closure` (`integration/review.rs:490–531`) reads each whole ODB object and maintains an in-memory seen set; reusing it does not by itself establish the proposed streaming memory bound for arbitrary large code closure. Require bounded traversal/verification work and reject exhaustion before canonical grants/refs. Do not enlarge the existing1MiB bound on newly created native package objects (`publication/store.rs:34,373–378,640–643`) merely to accommodate separately delivered code dependencies.

These are narrow missing operational rules in the proposed transport, not reasons to reopen the owner-policy or native fetch architecture.
