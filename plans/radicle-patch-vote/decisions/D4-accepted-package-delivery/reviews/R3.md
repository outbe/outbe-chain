## Search for a smaller existing path

I checked local receipt/control dispatch, contribution gossip, native fetch clone/pull and package persistence rather than assuming a new transport was needed.

1. Existing local socket connects only same-host node/sidecar. It cannot get missing remote witness/archive bytes by itself. Extending its bounded protocol is reuse, not an alternative remote path.
2. Existing OSIG public-contribution gossip is not a historical archive channel: `network/gossip.rs:114–143,154–174,187–214` requires current repository material and current member sender validation, and clears/drops inbox when current material is absent. Reusing that authentication for read-only history would violate the required no-current-Output/share behavior.
3. Native fetch exposes normal clone/pull with canonical validation, not a supported public Outbe-witness API. `radicle-node/src/worker/fetch.rs:42–94` selects existing-repo pull versus temporary clone, cleans unsuccessful clone and only moves a successful validated repository. Calling this path does not transport external witness or bypass the empty pinned identity. Reworking it to expose unvalidated packs/policy staging would touch the prohibited native fetch/storage seam and still leave external witness delivery unsolved.
4. Sending only manifest/witness then calling ordinary fetch is insufficient for a fresh store: native reconstruction needs owner identity, author patch graph, exact revision content and parent closure before proof. Existing test demonstrates that native fetch does not currently provide that prerequisite. Reusing a generic Git pack transfer API would need another integration and would not remove the public metadata exchange.

A request/chunk message type on the already registered channel is the smallest complete supported boundary I found. It introduces an archive protocol, but no new network service/port, trust authority, registry, quorum or SDK daemon. It should carry only what the existing accepted verifiers require.

## Concrete implementation constraints to retain

These clarify the proposed bounded mechanism and are evidence obligations, not permission to broaden it:

- Keep separate bounded archive queues/slots from OSIG inbox and publication mailbox. Existing `network.rs:813–870` actor and `send:1072–1085` share one physical channel; the quota alone is not priority or fairness. The stated promise that archive cannot block signatures must be implemented with scheduling/backpressure and demonstrated under simultaneous archive/signature load. Do not treat a plain common FIFO plus32msg/s as that proof. No extra physical channel is required to schedule bounded background chunks below control/signing traffic.
- Enforce the4387-byte entire frame bound before decode/allocation; chunks exclude header. The256 pending and5-second deadline must be finite per node/peer/request state, not repeated unlimited allocation for each incoming request. Read/export must run in bounded sidecar workers, never disk/Git work or awaiting chunks in the network actor. Same-UID/private socket checks (`local.rs:87–113`) remain.
- Interpret the proposed native fetch budget as the total bytes of one bounded archive operation/staging, not a fresh5GiB allowance for every chunk or every independently unbounded peer. `radicle-fetch/src/state.rs:28–30` default is5GiB. Request timeout should be per bounded chunk exchange; a whole5GiB transfer cannot be required to complete within5 seconds. Clean/reuse interrupted staging without allowing retries to grow retained unverified bytes indefinitely.
- Keep native object-row1MiB limits distinct from arbitrary pinned code blobs: `publication/store.rs:370–384` applies MAX_NATIVE_PAYLOAD to newly created manifest rows only. Pinned code/history objects may be larger and must be streamed under the aggregate fetch budget; do not accidentally reject valid repositories by applying the native-envelope payload cap to all Git content.
- On server, accepted receipt/public governments scope and verified reachability define exportable bytes. A peer-supplied arbitrary filesystem path/ref/OID must not become unrestricted disk/ODB export. On client, source lists never count as closure proof. Node and collector partial import/restart must retry idempotently; no grants/token may be issued from a merely downloaded directory or only one populated store.

These are bounded implementation choices within the proposal and existing plan. They do not require a new ownership/consensus policy or a new D4 alternative decision. If implementation cannot meet them on channel8, stop and return with concrete evidence rather than silently dropping them.
