## Why A is the smaller complete option

A uses the existing policy-aware repository/storage wrapper and native verification helpers as a shared boundary for candidate admission, then threads that boundary into APIs that currently retain raw Git or only SQL. It addresses an already accepted P2 requirement: every reachable managed-owner entry and its dependents must be authorized even through an Ed namespace, while independent ordinary Ed activity remains available. It adds no Vote semantics, signer/protocol format, validator lifecycle, or new feature.

B would change generic ChangeGraph loading from its current Option/best-effort behavior, introduce typed authorization propagation across generic storage/error callers, and define new dependency semantics for Resource/Related. `get`, `list`, `create/update` and downstream evaluator errors would all need compatibility work. It still cannot fix raw stream and SQLite readers without the same A-style wiring. I found no concrete source basis that makes B substantially smaller or more complete. Typed internal errors may still be used inside A; this does not require redesigning generic graph semantics.

A is not a single extra `authorize_entry()` call. Its minimal complete scope is the shared admission predicate plus all the existing authoritative entry/view callers above. Keeping only the original entry-local hook, or only changing graph traversal, relocates the gap.

## Required constraints for the user-facing proposal and subsequent implementation

These clarify the proposed A; they do not authorize implementation or alter the frozen proposal.

1. **Verify the right closure and classify it correctly.** Follow actual Git parents, including ordinary COB parents, Resource/Related, nested and cross-type dependencies, before filtering the requested COB type. Ordinary code commits are not all COBs and must not be required to have a manifest/owner receipt. Conversely, a malformed/unknown BLS native entry or missing reachable dependency must not be downgraded to an ordinary unsigned code commit and admitted. Reuse native parsers and exact reconstructed bytes. `raw.load` is not itself complete Ed verification: the shared boundary must preserve actual `valid_signatures()` verification before authoritative use, not trust an author/header or envelope echo.

2. **Admission must be per candidate, not per repository.** Deny the owner entry and every dependent candidate even when the outer namespace/author is Ed; admit independent pure Ed tips and exact revisions alongside them. Do not let best-effort graph pruning turn a denied dependency into a valid disconnected descendant. Do not reject all namespace refs merely because one tip fails. Treat an affected materialized object view as needing reevaluation from admitted sources, so unaffected valid activity can remain visible.

3. **Wire raw/direct/new-write callers explicitly.** Thread policy-aware storage into Stream/OpsIter and the CLI caller; keep all four stream range variants consistent. `Op::load(&Repository, id)` must use the predicate. Raw parsing/preparation helpers may remain raw, but user-facing managed reads cannot use them as admission. Include `DraftStore`, fresh and temporary repository opens, generic store get/list/ops, local `store/apply/update`, and fetch update boundaries. Never derive trusted context from native envelopes or delivering peer/namespace.

4. **Provenance belongs to the exact materialized view and is checked on every read surface.** Bind repository/object/type, exact admitted source-tip set, relevant owner-entry receipts/context and trusted policy identity/view needed for validation. Tips added/removed, cache warmed before policy installation, or a changed/missing provider cannot reuse a previous permissive decision. Validate writer and reader get/find/list/status/count plus lazy iterator rows and mutation reads (`get_mut`), not only direct get. A new valid pure Ed tip must cause the current view to refresh rather than silently returning stale data. Recompute from admitted Git where possible; do not bless a preexisting JSON row with invented provenance.

5. **Handle persistence without destructive reset.** Introduce a compatible cache migration/provenance record. Existing managed rows lacking provenance are untrusted until reevaluated; preserve unrelated Ed/static cache data. StoreReader has no writer, so it must use an available rebuild path through a writer, or return an explicit unavailable/denied result when current admission cannot be established. Data+provenance must represent the same source snapshot; do not save them across a tip/policy-view race and then present them as one validated view. Reopen/rebuild must revalidate rather than permanently trust a cached positive decision.

6. **Keep archive admission separate from latest promotion.** An immutable historical entry with its accepted historical receipt stays verifiable after membership/material changes. It must not be rejected merely because the receipt is not in the current generation. Admission/cache provenance alone cannot grant new canonical writes, restore old owner refs, or claim readiness. Existing design.md §4 latest complete snapshot, monotonic receipt sequence, finalized trusted view and promotion CAS checks remain separate mandatory checks, repeated at actual promotion.

The expected map should therefore explicitly name `radicle/src/cob/op.rs`, `radicle-cli/src/commands/cob.rs`, `radicle-fetch/src/state.rs`, cache schema/migration and **both** StoreReader/StoreWriter implementations in addition to the proposal's storage/store/stream/cache modules. These are actual callers of the existing P2 behavior, not new scope. A shared storage wrapper can avoid invasive generic graph rewrites; no exact new Rust API is prescribed by this decision check.
