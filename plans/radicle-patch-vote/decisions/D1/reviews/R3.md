## Обязательные уточнения при предложении A

1. **Полная зависимость — не просто один revwalk и не один typename.** Обходить actual Git parents и значимые Resource/Related ссылки, включая nested/mixed-type/cross-namespace owner entries. Frozen loader читает trailers отдельно и при load не доказывает, что каждый trailer OID — actual parent; нельзя предположить это только потому, что штатный writer так делает. Допустим либо обход semantic references, либо structural reject несовпадающей связи до использования. Обычные code commits в Related ancestry не являются COB и могут быть unsigned: нельзя пытаться загрузить каждый code commit как COB и отказать всей чистой Ed revision. При этом NativeContextRequired/invalid BLS header/denial нельзя трактовать как «это не COB, пропустить». Это уточнение boundary, не требование нового формата.
2. **Quarantine per tip/dependent branch, с native verification.** При denied tip не отдавать частично загруженный descendant evaluator/Op/stream; не отказывать всему repo. Независимые чистые tips, revisions и accepted ancestors остаются доступными по своим exact OIDs. Native cryptographic validity и trusted receipt для actual owner entry проверяются отдельно; доставивший namespace/actor envelope не заменяет ни одну из проверок. Missing object/dependency не даёт permissive admission. Повторные dependency visits можно memoize по immutable OID и trusted policy provenance; не нужна новая глобальная история/сервис.
3. **Provenance должен прийти от реально admitted evaluation и обновляться вместе с row.** Existing `Update<Patch/Issue>` имеет только rid/id/object. Нужно провести source-tip/provenance из store/evaluation через `Cache::write`, mutation/write-through и node `cache_cobs/update_or_remove`, а не восстановить разрешение из сериализованного Patch или arbitrary caller JSON. Чтения StoreReader **и** StoreWriter, итераторы и counts должны учитывать тот же admitted view. Provenance включает binding к repo/managed-policy и exact source tips/owner receipts; изменения источника, missing/unknown provider или несовпадающий binding требуют revalidation/rebuild/clear denial. Нельзя валидировать один tip set, затем сохранить или вернуть state другого tip set. Это обычная согласованность выбранного snapshot, не новая finality feature.
4. **Legacy rows и read-only handles.** Новые поля/migration не могут считать старую managed row доверенной по default. Без provenance — rebuild через admitted Git либо явный denial, если он недоступен. Read-only StoreReader не должен тихо bypass ради невозможности записать migration; допустим safe re-evaluation без доверия старой row либо clear error. Сохранить ordinary Ed/static native данные и caching. Existing `write_all` очищает rows одного repo перед заполнением; не превращать security migration в destructive global reset и не оставлять половину обновлённого materialized state authoritative после отказа.
5. **Historical admission отдельно от latest promotion.** Уже authenticated accepted immutable entry не теряет historical право чтения при обычной смене current epoch/material. «Stale cache» означает несоответствие source view/provenance, а не автоматический отзыв accepted history. Admission old receipt не даёт право latest refs rollback/new write. Finalized latest snapshot/freshness/CAS остаются отдельным обязательным publication gate; owner-entry closure helper не должен выдавать promotion permission. Generic Heartwood получает trusted facts через provider, без Vote/epoch логики.

Пункты 2–5 уже следуют из proposal/действующего P2 scope; их нужно сохранить явно при согласовании/реализации. Пункт1 устраняет возможное слишком узкое толкование слов «Git closure». Эти уточнения не требуют нового P0 решения или расширения пользовательской фичи. Frozen proposal мной не менялся.
