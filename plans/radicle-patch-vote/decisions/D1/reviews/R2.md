## A против B и обязательные уточнения к предложению пользователю

A реализуема по существующим seams: repository-aware storage уже знает managed owner/provider и native load; `objects()` определяет evaluator tips; Cache уже содержит Git Store, поэтому может получить authoritative source view; stream callers можно провести через trusted repository. Это один admission predicate и его adapters, а не отдельные rules для каждого COB action. Можно сохранить generic graph best-effort поведение для уже admitted entries. Рекурсивный обход следует делать поверх raw Git/native primitives, не рекурсивно вызывать тот же gated public load без отдельного traversal state.

B может улучшить typed diagnostics и pruning, но сам по себе не защищает `Op::load`, raw streams и SQL queries. Кроме того, Resource/Related могут указывать на другие COB types или обычные code commits: превращение всех таких связей в same-object CRDT edges меняет legacy evaluation semantics. Источники не дают основания считать B меньшим полным исправлением. Не предлагаю новый альтернативный feature или protocol format.

До реализации и при представлении A нужны следующие точные оговорки, а не обещание уже доказанной безопасности:

1. **Определить closure и per-tip результат.** Проверять реальные Git parents рекурсивно, Resource/Related references и cross-type dependencies до manifest/type/range filtering. Проверка не ограничивается `Entry.parents`, внешним namespace или текущим entry author. Обычный code commit сам по себе не обязан быть COB; его нельзя отклонять лишь за отсутствие COB manifest. Owner распознаётся по настоящему native объекту/author, затем exact native bytes/repository/context проверяются существующим verifier с trusted authorization. Не принимать envelope.context или SQL provenance как self-authenticating receipt. Outbe-specific правила внутри generic evaluator для этого не требуется.
2. **Указать fetch map/transaction boundary явно.** В map добавить `radicle-fetch/src/state.rs` и его `Cached::validate_remote`, `sigrefs.rs`, конечный `repository::update`, а для local update — `storage/git/cob.rs` object update/DraftStore и `object/collaboration/update.rs:124` как actual caller. Текущий fetch prune работает по remote и signed refs подписывают точную map. Нельзя произвольно вычеркнуть один ref и назвать оставшуюся map тем же signed snapshot; нельзя считать существующий remote-wide prune готовой реализацией per-tip quarantine. Разделить transport/map verification, admitted COB tips и managed canonical promotion; показать тестом, как независимые pure Ed tips остаются доступны при bad tip того же remote/COB. Также проверить допустимый Ed prefix/revision без второй удобной ref, иначе blanket tip rejection может скрыть разрешённую историю. Не выдавать raw quarantined object/ref за authoritative owner state.
3. **Cache boundary включает обе access modes и источники заполнения.** Добавить StoreWriter get/find/list/status/count, Cache::get_mut/update, direct construction в CLI cache commands и migrations/shared cache Store. Старые id/repo/JSON rows не имеют required provenance. Привязка должна описывать exact admitted source tip set и owner entry receipt provenance, из которых получен материализованный объект; повторная проверка должна обнаружить смену source view. Нельзя лишь проверить, что какой-то receipt когда-то разрешал один owner, затем вернуть старую SQL state. Revalidation должна определять единый admitted view для get/find/list/status/count и не давать aggregate count от запрещённых rows.
4. **Read-only и mixed-view fallback описать до обещания минимальности.** StoreReader физически не может выполнить writable rebuild. Безопасный вариант в существующем scope — читать/re-evaluate admitted Git history через уже содержащийся Store либо вернуть явную ошибку там, где source/proof недоступны; записать provenance можно через writer. Для независимого pure Ed source отсутствие managed-owner provider/checkpoint само по себе не должно блокировать чтение. При mixed history возврат admitted части/rebuild предпочтительнее blanket managed-repo denial. Не использовать нынешний `write_all -> remove_all` как глобальную security invalidation, не удалять permissive Ed/static BLS rows или repo data.
5. **Не смешать историческую provenance с current promotion.** Exact accepted historical owner entry остаётся допустимым после смены validator material, если trusted immutable receipt проверен. Это не разрешает retired key новое действие и не делает historical signed refs latest. Missing trusted policy для managed dependency закрывается fail-closed, а CAS/latest/finality проверка остаётся отдельной при ref promotion и повторяется в соответствующей transaction boundary. Memoized admissions/cache bindings не могут переживать смену relevant trusted view без revalidation.

Это уточнения существующего A/P2 контракта и proof map. Они не требуют в D1 реализации новых действий, новых signatures, новых roles или chain logic внутри Heartwood. Без них утверждение «все local/fetch/cache/direct paths исправлены per-tip» было бы преждевременным.
