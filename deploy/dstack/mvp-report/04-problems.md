# Проблемы и решения

Сгруппировано по источнику. В каждой строке: что наблюдалось, причина, что
сделано. Хронология и доказательства — в `notes/progress-journal.md`.

## 1. dstack и симулятор

| Проблема | Причина | Решение |
|---|---|---|
| Проверяющий dstack в симуляторе даёт `is_valid: false` | в симуляции VMM не выдаёт документ измерений, измерение — заглушка | проверка измерения образа перенесена на железо |
| `/root` в госте только на чтение | устройство образа | ключ SSH для `dev` кладётся в `/etc/ssh` |
| VMM не стартует | нет `qemu-img`; помощнику сети нужен `virsh` | пакеты `qemu-utils`, `libvirt-clients` |
| Интерфейс отчётов в симуляторе принимает только имена с префиксом `dstack-` и не поддерживает усечение файла | это FUSE симулятора, не ядро | имя записи `dstack-outbe-…`, запись без усечения |
| Симулятор подписывает сертификаты ECDSA P-384, проверка их отклоняет | настоящие сертификаты AMD — RSA-PSS; крейт `sev` без OpenSSL знает только его | сквозной прогон только на железе (Р20, вариант А); в симуляторе — модульные тесты на настоящем отчёте |
| В симуляторе нет `/dev/sev-guest` | — | производный ключ проверялся только на железе (позже снят вовсе) |
| Контейнерная сборка `outbe-genesis-cli` не работает на хосте | в бинарник вшит путь `/workspace/…/profiles` | генерация сети бинарниками хостовой сборки |

## 2. Сеть VM

| Проблема | Причина | Решение |
|---|---|---|
| Проброс портов не подходит для консенсуса | транспорт сверяет адрес источника с адресом пира | мост, у каждой VM свой адрес |
| VM после перезапуска получает другой адрес | гость представляется новым client-id | `dnsmasq --dhcp-ignore-clid`, адреса закреплены за MAC |
| Церемония падает по таймауту (`acks: 1/3`) | настройки `recommended` отвергают частные адреса | `--consensus.use-local-defaults` |
| Нода не стартует без интернета | скачивает CRS Barretenberg | файл раздаёт сервер бандлов; для боевого образа — запечь в образ |
| Кончились адреса DHCP (41 из 41) | бессрочные аренды при многократном пересоздании VM | сброс аренд |
| Пользовательская конфигурация с `external_address` не разбирается | JSON собирался без кавычек (скрипт развёртывания) | исправлено |

## 3. Платформа AMD

| Проблема | Причина | Решение |
|---|---|---|
| SNP выключен на хосте | параметр ядра `iommu=pt` | убран |
| `/dev/sev` недоступен | принадлежит root | правило udev, группа `kvm` |
| Гость падает в `dstack-prepare`: `Skipped bytes were expected to be zeroed` | отчёт версии 5 (прошивка API 1.58), `sev` 6.0.0 его не знает | `sev` 8.0.0 у нас и патчем в dstack |
| Сертификатов AMD в госте нет | хост не передаёт таблицу сертификатов | VCEK скачивается из службы AMD и кладётся в бандл |
| Запрос производного ключа отклонён | `sev` 8 шлёт версию 2 сообщения и требует mitigation vector | закреплена версия 1 |
| Атрибут `provider` не найден | в настоящем ядре он в каталоге запроса | исправлено чтение |
| Порядок байт GUID в таблице сертификатов | хранятся в порядке текстовой записи | исправлено по таблице симулятора и коду `sev` |

## 4. Платформа Intel

| Проблема | Причина | Решение |
|---|---|---|
| TDX не поднимается на хосте | нужны параметры ядра | `nohibernate kvm_intel.tdx=1` |
| Гость зависает на «requesting app keys» | QGS не может получить сертификат PCK: нет PCCS, платформа не зарегистрирована у Intel | локальный PCCS, регистрация с хоста (с согласия владельца) |
| Квота длиннее канонической на 307 байт | ядро отдаёт хвост после данных подписи | нода обрезает |
| После перезапуска VM сервис не открывает состояние: `bad sealing key` | при `key_provider: none` агент dstack после загрузки выдаёт другой ключ | состояние на диск больше не пишется (Р30) |

## 5. Протокол и код

| Проблема | Причина | Решение |
|---|---|---|
| Регистрация в режиме SEV-SNP невозможна | `quote_report_data` в сервисе принимал только режим SGX | исправлено (r6) |
| Валидатор не возвращается после перезапуска VM | повторный вход при действующей записи запрещён; запись живёт 14 суток | Р26: повторный вход разрешён в режимах VM при том же ключе NodeHost, свежих идентификаторах и свежем доказательстве |
| `tee join` падает после успешной регистрации | CLI считал собственную прежнюю запись конкурирующей | конкурирующей считается запись с версией не ниже нашей |
| Нода после входа не стартует: `validator recovery requires UpstreamBootstrap` | нужен `--upstream` | поле `upstream_url` в конфигурации, скрипт запускает ноду с ним |
| Смешанная сеть падает на блоке 1: `OST3 submission does not prove one canonical committee registration` | два сравнения «вид доказательства равен режиму сети» | заменено на `admits_evidence` |
| Нода падает с переполнением стека | при переносе скриптов в образ потерян `RUST_MIN_STACK` | возвращён |
| Тесты реестра «зелёные», но исполнялось 4 теста | запускались без признака `tee-attestation-v1` | запуск с `--all-features` (64 теста); фикстура берёт режим из политики |
| Сборка сервиса без `sev-snp` сломана | новый модуль без вызывающего кода, предупреждение — ошибка | атрибут на объявлении модуля (r16) |
| Тест `transport/tests/onboarding.rs` с `native-dcap` не компилируется | в инициализаторе нет поля `transition_key_ready_proof` | **не исправлено**: так и в `main`, файл не наш |

## 6. Защита ключа от оператора

До r13 оператор мог получить ключ у работающей сети четырьмя путями (аудит,
записка «дополнение 4»):

| Путь | Суть | Чем закрыт |
|---|---|---|
| 1. Свой корень сертификатов | политика с корнем приходила от ноды, а нодой управляет оператор; проверка доверяла корню из доказательства, если хэш совпал с политикой | Р28: корни AMD и Intel закреплены в коде проверки |
| 2. Запечатанное состояние на диске | на SEV-SNP производный ключ не зависит от манифеста: VM с тем же образом и своим манифестом читала чужое состояние | Р30: ключ только в памяти, на диск ничего не пишется |
| 3. Правило выдачи из запроса ноды | сервис брал политику выдачи у собственной ноды | Р29: правило — из измеряемого манифеста VM |
| 4. Поддельный описатель сети | сервис принимал описатель с диска | Р31: хэш описателя в манифесте |
| VM с оболочкой | образ `dev` проходил бы как допустимый | Р32: в списке манифеста только `prod` |

Дополнительно: экспорт ключа для обновления образа в VM отключён.

Остался открытым путь через основание сети (ТД-5): церемония создания ключа
не проверяет аппаратные доказательства участников. Он есть и в схеме на SGX.

## 7. Эксплуатация образа без входа

| Проблема | Причина | Решение |
|---|---|---|
| Валидатор не возвращается после перезапуска во время незавершённой попытки входа | записи попытки (`replacement-*`) на диске блокируют новую, а прежнего сервиса уже нет | скрипт удаляет их перед первой попыткой нового сервиса; файл запроса перенесён в память (r15). Правильное место — CLI (ТД-12) |
| Ключ p2p обнулён после принудительной остановки | скрипт переписывал файл на месте при каждом старте | скрипты не пишут в файлы ключей; очищенная копия в памяти (r15) |
| Причину отказа сервиса на `prod` не узнать | вывод сервисов не идёт на консоль | не решено (ТД-11); причины читались на VM `dev` |
| Устаревшая надпись сервиса | не обновлена после Р31 | исправлена (r14) |
| Чтение диска после принудительной остановки даёт «Bad message» | журнал ext4 не проигран (`noload`) | чистое чтение — после штатной остановки |

## 8. Процесс

| Проблема | Что произошло | Вывод |
|---|---|---|
| Широкие сборки Rust на общей машине | нагрузка мешала другим сессиям | одна тяжёлая задача за раз, `nice -n 19 ionice -c3`, `-j 2..4` |
| Цикл «исправление → новый образ» | r14, r15, r16 из-за ошибок, которые ловятся до сборки | сначала тесты и VM `dev`, сборка один раз |
| Преждевременное «готово» | дважды объявлялось до сверки с критериями цели | итог объявляется после прогона всех критериев на итоговом образе |
| Потеря кворума тестовой сети | остановка второго валидатора при недоступном первом; скрипт без ожидания остановки и без `upstream_url` | в сети из 4 одновременно недоступен может быть один |
| Утверждённое решение противоречит факту | Р7 (один крейт `sev` 6) против отчёта версии 5; «KMS не используем» против запечатывания на TDX; «состояние в tmpfs» против запрета повторного входа | каждое — остановка и решение владельца |
| Образ собран до коммита | бинарник ноды вшивает идентификатор коммита | образ для выпуска собирать после коммита |
