# Как собран образ VM

Команды и подробности — в `deploy/dstack/README.md` репозитория. Здесь —
устройство и причины решений.

## Основа

- dstack, ревизия `c88f60e781a62d542e0843b333f18a48d1458b88` (ветка `next`,
  версия 0.6.3). Используется только как подложка: VMM, гостевая ОС (Debian),
  выдача отчётов процессора. KMS, gateway и контракты dstack не используются.
- Гостевая ОС собирается штатной сборкой dstack (`os/mkosi/repro-build`).
- Наше — наложение на дерево dstack: два патча и каталог `rootfs/`.

## Что добавлено к dstack

| Что | Файл | Зачем |
|---|---|---|
| Параметры ядра `dstack.storage_encrypted=false dstack.storage_fs=ext4` | `patches/0001-unencrypted-ext4-data-disk.patch` | диск данных без шифрования (допущение MVP); параметры ядра задаются только при сборке и входят в измерение |
| Крейт `sev` 8.0.0 в гостевых инструментах dstack | `patches/0002-sev-crate-8-report-version-5.patch` | прошивка SEV-SNP API 1.58 выдаёт отчёт версии 5; `sev` 6.0.0 его не разбирает, VM не загружается |
| Бинарники | `/usr/local/bin/` | `outbe-chain`, `outbe-radicle`, `outbe-cli`, `outbe-feeder`, `outbe-tee-enclave`, а также `outbe-tee-enclave-mock` и `outbe-tee-enclave-local-e2e` для сети без железа |
| Библиотеки `libc++`, `libc++abi`, `libunwind` | `/usr/local/lib/outbe/lib/`, `etc/ld.so.conf.d/outbe.conf` | бинарникам они нужны, в Debian образа их нет; берутся из образа сборщика, не с хоста |
| Скрипты запуска | `/usr/local/lib/outbe/provision.sh`, `run-role.sh` | вся логика запуска внутри образа и поэтому измеряется |
| Юниты systemd | `outbe-{provision,enclave,radicle,node}.service` | запускаются манифестом (`runner: bash`) |

Docker остаётся в образе, но валидатор его не использует: три наших процесса
запускает systemd.

## Два шага сборки

1. **Бинарники** — `deploy/dstack/build-binaries.sh`. Сборка в закреплённом
   образе `Dockerfile.project-toolchain` (базовые образы по digest, снимок
   архива Ubuntu, rustc 1.96), фиксированные пути (`/workspace`,
   `--remap-path-prefix`), `LANG=C`, `TZ=UTC`, `SOURCE_DATE_EPOCH` = время
   коммита `HEAD`. Источник — снимок рабочего дерева как git-tree.
2. **Образ** — `deploy/dstack/build-image.sh`. Клонирует dstack на закреплённую
   ревизию, накладывает патчи и `rootfs/`, копирует бинарники из шага 1, делает
   локальный коммит с фиксированными автором и датой, запускает сборку dstack.
   `FLAVORS="dev prod"` даёт оба варианта.

Оба шага имеют режим `--check`: две сборки с нуля и побайтное сравнение.

Признаки сборки:

| Пакет | Признаки | Причина |
|---|---|---|
| `outbe-chain` | `production-enclave`, `test-protocol-overrides` | genesis из профиля testnet содержит `config.outbeProtocol`; без второго признака нода его отвергает |
| `outbe-tee-enclave` (боевой) | `sev-snp`, `native-dcap` | `sev-snp` — работа в защищённой VM на обеих платформах; `native-dcap` — библиотека Intel для проверки квот TDX |
| `outbe-tee-enclave` (варианты без железа) | `local-e2e` | даёт `-mock` и `-local-e2e` |

## Варианты образа

| Вариант | Вход | Назначение |
|---|---|---|
| `dev` | SSH (ключ в манифесте), симулятор TEE | отладка, чтение состояния изнутри, VM «атакующего» в отрицательных проверках |
| `prod` | нет | всё, что считается результатом MVP |

У вариантов разные измерения. Правило выдачи ключа принимает только образы,
перечисленные в манифесте сети; в сетях MVP это `prod`.

## Что измеряется и что нет

| Часть | Защита |
|---|---|
| Ядро, initrd, командная строка ядра | входят в измерение запуска |
| Корневая файловая система (все программы и скрипты) | squashfs только на чтение под dm-verity; корневой хэш в командной строке ядра |
| Манифест `app-compose.json` | его SHA-256 привязан к отчёту: TDX — `MRCONFIGID`, SEV-SNP — `HOST_DATA` |
| Описатель сети | его хэш записан в манифест (раздел `outbe_release`) |
| Пользовательская конфигурация (`/dstack/user_config`) | не измеряется; скрипты читают её как данные и проверяют каждое поле |
| Диск данных `/dstack/persistent` | не измеряется и не шифруется; оператор может читать и менять |

Формулы привязки манифеста (сверены с настоящими значениями обоих серверов):

- TDX: `MRCONFIGID = 0x01 ‖ sha256(app-compose.json) ‖ 15 нулевых байт`;
- SEV-SNP: `HOST_DATA = sha256("dstack-mr-config-v3:" ‖ 0x00 ‖ документ)`, где
  документ — JSON с полями `app_id` (первые 20 байт хэша), `compose_hash`,
  `key_provider: "none"`, `version: 3`.

В манифесте стоит `no_instance_id: true`: без него в привязку входит
идентификатор экземпляра и значения у валидаторов разные.

## Размещение данных в госте

| Путь | Где | Что |
|---|---|---|
| `/dstack/persistent/outbe/` | диск данных | распакованный бандл, данные цепи, Radicle, журналы ноды |
| `/run/outbe/tee/` | память VM (tmpfs) | состояние сервиса; пусто после каждого старта |
| `/run/outbe/` | память VM | очищенная копия ключа p2p, файл запроса на вход |
| `/dstack/.host-shared/app-compose.json` | общий с хостом каталог | манифест; сервис сверяет его со своим измерением |

## Запуск внутри VM

1. `outbe-provision`: читает пользовательскую конфигурацию, скачивает бандл по
   `bundle_url`, отвергает архив, если в нём что-то кроме обычных файлов и
   каталогов, распаковывает на диск данных.
2. `outbe-enclave`: сервис. В режиме `confidential-vm` стартует с
   `--platform auto --network-descriptor … --app-manifest …` и отказывается
   работать, если манифест не тот, что привязан к измерению, образ VM не в
   списке манифеста или описатель сети не тот.
3. `outbe-radicle`, `outbe-node`.
4. Если сервис этой загрузки новый, а в каталоге ноды есть прежняя регистрация,
   скрипт сам выполняет `outbe-cli tee join` через `upstream_url` и запускает
   ноду с этим upstream.

## Воспроизводимость: что установлено

- Две сборки с нуля из одного исходника дают одинаковый `os_image_hash` для
  `dev` и `prod` и побайтно одинаковые бинарники (проверено для r14, r15, r16).
- Обе сборки каждый раз делались на одной машине. Сборка на второй машине не
  делалась.
- Правка документации хэш образа не меняет.
- Правка любого файла Rust меняет бинарник, даже если код не сдвинулся:
  компилятор вкладывает контрольную сумму исходного файла в отладочные данные.
- `outbe-chain` вшивает идентификатор и дату коммита. Образ, собранный до
  коммита и после него, различается этим одним бинарником и, значит, хэшем.
