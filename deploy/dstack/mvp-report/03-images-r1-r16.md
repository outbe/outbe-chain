# История образов r1–r16

Каждый образ — полная сборка (бинарники 20–30 минут, образ 30–45 минут, с
проверкой воспроизводимости вдвое дольше). Номер менялся при каждом изменении
содержимого образа.

## Сводка

| Образ | Что внутри | Почему понадобился | Итог |
|---|---|---|---|
| r1 (`outbe-validator-dev`) | dstack + бинарники обычной сборки, `dev` | первый образ | сеть из 4 VM в симуляторе, режим без аттестации |
| r2 | то же, бинарники из воспроизводимой сборки | задачи «воспроизводимые бинарники и образ» | хэши бинарников в госте совпали со сборкой |
| r3 | + абстракция источника отчёта, проба `--probe-attestation`, проверка отчёта SEV-SNP | образ для первого запуска на железе | проба работает в симуляторе |

## Подробно: что ломалось

### r1–r3. Симулятор

Работа шла на машине без TEE. Найдено:

- бинарь ноды без `test-protocol-overrides` отвергает genesis профиля testnet;
- нода скачивает CRS из интернета, а у VM его нет;
- VM после перезапуска получает другой адрес;
- консенсус с настройками по умолчанию отвергает частные адреса;
- в симуляторе измерение образа — заглушка, поэтому проверка «образ равен
  ожидаемому» возможна только на железе.

Вывод по этапу: симулятор проверяет раскладку и скрипты, но не аттестацию.

### r4 → r5. Первое железо AMD

Причина: dstack и наш код использовали крейт `sev` 6.0.0, который не знает
отчёт версии 5. Гость падал в `dstack-prepare`: `Skipped bytes were expected
to be zeroed`. В симуляторе отчёт версии 2, поэтому раньше это увидеть было
нельзя.

Вторая причина: функция сервиса, формирующая данные отчёта, принимала только
режим SGX; регистрация в режиме SEV-SNP была невозможна в принципе.

Решение: `sev` 8.0.0 у нас и патчем в dstack (с согласия владельца — это
отступление от утверждённого решения Р7).

### r5 → r6. Отличия настоящего ядра от симулятора

- Атрибут `provider` интерфейса отчётов в настоящем ядре лежит в каталоге
  запроса, а не в каталоге интерфейса.
- `sev` 8 запрашивает производный ключ сообщением версии 2 и требует поле,
  которого у прошивки нет; закреплена версия 1.

На r5 это обходилось исправленным бинарником на диске данных. r6 — то же
внутри образа.

### r6 → r7. Скрипты в образе

До r7 скрипты запуска приезжали в бандле на диск данных, то есть оператор мог
подменить их. Владелец назвал это обязательным для MVP. Скрипты перенесены в
образ, бандл стал только данными.

Дефект r7: при переносе потеряна переменная `RUST_MIN_STACK=16777216`, нода
падала с переполнением стека.

### r7 → r9. Изменения протокола

На TDX выяснилось: после перезапуска VM валидатор вернуться не может.
Состояние сервиса не переживает перезапуск, а повторная регистрация при
действующей записи запрещена (`finalized enclave lease is live`). Запись
основателя живёт 14 суток.

Решения владельца: разрешить повторный вход при действующей регистрации (Р26)
и сделать смешанный режим, принимающий доказательства обеих платформ (Р27).
r8 начали собирать с Р26, остановили: Р27 был готов раньше, чем сборка
закончилась. r9 содержит оба.

### r9 → r10. Повторный вход на железе

- Реестр принял повторную регистрацию, но `outbe-cli tee join` завершился
  ошибкой: принял собственную прежнюю запись за конкурирующую.
- Нода после входа требовала `--upstream`, а в скриптах образа его не было.

На r9 это обходилось CLI с диска и ручным запуском. r10 — оба исправления в
образе.

### r10 → r13. Смешанная сеть и защита ключа

Смешанная сеть на r10 прошла обе церемонии и упала на первом блоке: два
сравнения в коде требовали, чтобы вид доказательства совпадал с режимом сети.
В смешанном режиме это неверно. Исправлено.

В это же время владелец указал, что защита ключа от оператора — цель MVP, а не
техдолг. Аудит показал четыре пути к ключу для оператора. Решения Р28–Р32:
закреплённые корни AMD и Intel, правило выдачи из измеряемого манифеста, ключ
только в памяти, описатель сети в манифесте, счёт только образа `prod`. r13 —
первый образ с этим и первый, проверенный в варианте без входа.

### r13 → r14. Одна строка

Сервис при старте печатал устаревшую надпись «описатель сети НЕ измеряется».
На поведение не влияет. Образ пересобран, потому что объявлялся итоговым.

### r14 → r15. Два дефекта возврата валидатора

Найдены при повторе отрицательных проверок на итоговом образе.

1. **Вход после незавершённой попытки.** `tee join` хранит записи попытки на
   диске, чтобы продолжить её после перезапуска. В VM состояние сервиса только
   в памяти: прежнего сервиса нет, продолжать нечего, а записи блокируют новую
   попытку. Валидатор не возвращался после любого перезапуска во время
   незавершённой или отклонённой попытки.
2. **Потеря ключа p2p.** Скрипт при каждом старте ноды переписывал файл ключа
   на месте. Принудительная остановка VM в этот момент оставляла файл пустым.
   Нода в цикле перезапуска переписывала его каждые 5 секунд, поэтому окно
   широкое.

Оба — уровня «валидатор теряется», оба в скриптах образа.

### r15 → r16. Сломанная сборка

Сверка с критериями цели потребовала прогнать тесты всех затронутых крейтов.
Тесты реестра не собрались: реестр собирает сервис без признака `sev-snp`, а
новый модуль в этом наборе не имеет вызывающего кода; предупреждение о
неиспользуемом коде — ошибка. То есть сборка сервиса без поддержки VM,
включая вариант для SGX, была сломана.

Исправление — один атрибут. Но правка файла Rust меняет бинарник, поэтому
итоговый исходник перестал воспроизводить r15. Две попытки сохранить бинарники
прежними не удались. Образ пересобран как r16 и все проверки повторены.

## Почему образов получилось столько

| Причина | Образы | Можно ли было избежать |
|---|---|---|
| Факты, видимые только на железе | r5, r6 | нет: симулятор их не показывает |
| Решения и требования, появившиеся по ходу | r7, r9, r13 | нет |
| Дефект переноса или интеграции, найденный уже в образе | r8 (стек), r10, r11 | да: проверкой на VM `dev` с подложенным бинарником до сборки |
| Пересборка итогового образа ради мелочи | r14 | да: надпись не стоила образа |
| Дефекты, которые ловятся тестами или сценарием на `dev` | r15, r16 | да: полный прогон тестов и отрицательных сценариев до сборки |

Правило, принятое после замечания владельца: сначала тесты и проверка на VM
`dev`, сборка один раз; после итогового образа пересборка только при дефекте
уровня «валидатор теряется» или «ключ утекает».
