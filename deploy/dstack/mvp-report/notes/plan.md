# План: MVP outbe-chain на dstack (сначала без TEE, затем AMD SEV-SNP)

## Контекст

Цель — проверить, что валидатор outbe-chain может жить в конфиденциальной VM под
dstack вместо SGX-анклава под Gramine, и что сеть из четырёх таких валидаторов
проходит DKG, регистрацию анклавов и расшифровку оффера.

Принятые решения (не пересматриваются в этом плане):

- Платформа — self-hosted dstack, только как подложка: VMM, гостевая ОС, выдача
  отчётов. KMS, gateway и контракты dstack не используются.
- В образе три наших процесса: `outbe-chain`, `outbe-radicle`, анклав. Запуск
  раннером `bash`, без Docker для нашего приложения.
- Анклав остаётся отдельным процессом; канал нода↔анклав остаётся как есть
  (Noise поверх TCP на loopback). Замена на raw TCP — после MVP.
- Диск данных без шифрования. Sealing нет: после рестарта VM ключ ставится
  заново через `outbe-cli tee join`.
- Сначала всё делается на этой машине в режиме dstack без TEE (симулятор).
  Настоящая проверка — на заказанном AMD-сервере (SEV-SNP).

Что выяснено чтением кода и меняет порядок работ:

- Первая веха достижима без правок протокольного кода: у анклава есть сборки
  без SGX, а сеть в режиме `gramine-direct-dev` регистрирует анклавы по подписи,
  без квоты.
- Симулятор dstack умеет платформу `dstack-amd-sev-snp` на обычном хосте, то
  есть AMD-путь отлаживается здесь, до прихода сервера.
- Готовая раскладка «один валидатор на одну машину» уже есть:
  `outbe-genesis-cli create network.yaml` выдаёт на каждого валидатора архив с
  ключами, genesis, скриптами запуска и systemd-юнитами.
- Проверка квоты при `registerEnclave` выполняется внутри анклава каждого
  валидатора во время исполнения блока; допустимые измерения задаются в genesis
  (`outbe-chain tee genesis`). Новый тип аттестации встраивается в эту же схему.

## Общие правила исполнения

- Машина общая: на ней работают другие сессии агентов, CI-раннеры и процессы
  под `/opt/outbe`. Их не трогаем. Сборку образа ограничиваем `JOBS=8`.
- **Отдельная ветка.** Все изменения в репозитории идут только в ветку
  `mvp-tdx-dstack`; в `main` ничего не попадает. Ветка уже создана от `main`
  (коммит `607751fc9`). Перед началом этапа 2 она обновляется от свежего `main`.
- Работа с веткой — в отдельном git worktree (`~/outbe-chain-mvp-tdx`), чтобы
  не переключать ветку в `~/outbe-chain` под другими сессиями.
- Копия этого плана лежит в `~/dstack_plan.md`.
- Всё стороннее (клон dstack, образы, состояние VM) — в `~/outbe-tdx-mvp/` и
  `~/.dstack-vmm/`, вне репозитория.
- Коммиты и push — только по отдельной команде.
- Этапы 0–3 не меняют протокольный код. Если на них понадобится правка
  протокола, формата на проводе или ABI — остановка и доклад.

## Этап 0. Подготовка хоста

1. Установить `qemu-system-x86`, `swtpm`, `swtpm-tools` (сейчас отсутствуют).
2. Проверить доступ к `/dev/kvm` на чтение и запись.
3. Склонировать dstack в `~/outbe-tdx-mvp/dstack` на коммит `c88f60e`
   (ветка `next`). Каталог сборки не должен лежать на overlayfs.
4. Проверить запас: диск (сейчас свободно 124 ГБ, сборке нужны десятки ГБ),
   память под четыре VM (сейчас доступно около 31 ГБ).

Готово, когда: QEMU и swtpm на месте, KVM доступен, клон на нужном коммите.

## Этап 1. Стоковый dstack в режиме симуляции

Цель — убедиться, что цепочка dstack работает на этой машине до наших изменений.
Шаги по `docs/development-without-tee.md`:

1. Собрать dev-образ: `FLAVORS=dev JOBS=8 ./os/mkosi/repro-build/repro-build.sh -o <dir>`
   (30–45 минут, нужен привилегированный Docker).
2. Собрать `dstack-vmm` и `supervisor` (`cargo build --release -p dstack-vmm -p supervisor`),
   поставить их и `vmm-cli.py` в `~/.local/bin`.
3. Настроить `~/.dstack-vmm/vmm.toml`: путь к образам, `qemu_path`,
   `[cvm.networking] mode = "user"`, `[cvm.port_mapping] enabled = true` с
   диапазонами TCP и UDP, `[cvm.tee_simulator]` с собственным случайным seed,
   путь к `supervisor`.
4. Поднять сервер тестового collateral (`dstack-mock-attestation serve`).
5. Развернуть пробную VM из их документа с `--simulated-tee dstack-amd-sev-snp`.
6. Внутри VM вызвать `/v1/Attest` и проверить ответ их `dstack-verifier`,
   настроенным на тестовые корни (`insecure_allow_external_trust_anchors = true`).

Готово, когда: VM доходит до `Boot Progress: done`, `/v1/Attest` возвращает
аттестацию с платформой `sev-snp`, верификатор dstack её принимает.

## Этап 2. Наш образ, одна VM

Новый каталог в репозитории: `deploy/dstack/` (ветка `mvp-tdx-dstack`).

| Файл | Назначение |
|---|---|
| `patches/` | правки к дереву dstack (см. ниже) |
| `rootfs/` | наши systemd-юниты и preset-файл |
| `build-image.sh` | клон dstack на закреплённый коммит, наложение правок, копирование бинарей, локальный коммит во временном клоне, запуск `repro-build.sh` |
| `app-compose.json` | манифест с `runner: bash` |
| `README.md` | как собрать и запустить |

Правки к дереву dstack (все измеряются, поэтому входят в образ, а не в конфиг VM):

- `os/image/kernel-cmdline.sh`: добавить `dstack.storage_encrypted=false` и
  `dstack.storage_fs=ext4`. Параметры ядра задаются только при сборке.
- `os/mkosi/mkosi.conf`: добавить runtime-библиотеки наших бинарей
  (ожидаются `libc++1`, `libssl3`; точный список — по `ldd`).
- `os/mkosi/mkosi.skeleton/`: бинарники в `usr/local/bin`, юниты в
  `usr/lib/systemd/system`, preset `80-dstack-outbe.preset`. В имени preset-файла
  должно быть `dstack`, иначе сборка его удаляет.

Юниты — на основе тех, что генерирует `outbe-genesis-cli`
(`bin/outbe-genesis-cli/src/launch_bundle/`: `run-enclave.sh`, `run-radicle.sh`,
`run-node.sh`, `outbe-{enclave,radicle,node}@.service`), с тремя отличиями:

- данные ноды и Radicle лежат на диске данных: `/dstack/persistent/outbe/…`;
- каталог анклава `--tee-dir` лежит на tmpfs (`/run/outbe/tee`): он живёт до
  рестарта VM, после рестарта пуст — это и есть «без sealing»;
- добавляется юнит первичной раскладки: если `/dstack/persistent/outbe` пуст,
  он забирает архив валидатора по адресу из `/dstack/user_config` и распаковывает.
  Это механизм MVP; боевой способ доставки ключей в этот план не входит.

Манифест `app-compose.json` пишется вручную (их CLI умеет только docker-compose):
`runner: bash`, `key_provider: none`, `secure_time: false`, `storage_fs: ext4`,
`bash_script` из одной строки `systemctl start …`.

Бинарники — обычная release-сборка из репозитория (glibc, динамическая линковка);
гостевой образ на Debian trixie новее хоста сборки, совместимость проверяется `ldd`.

Готово, когда: VM с нашим образом загружается, три юнита активны, после
`dstack stop` / `dstack start` данные на `/dstack/persistent` на месте, а каталог
анклава пуст.

## Этап 3. Четыре валидатора, без правок протокольного кода

1. Ключи: `outbe-keygen validator` на четырёх валидаторов.
2. Genesis и архивы: `outbe-genesis-cli create network.yaml` с `tee.mode: gramine-direct-dev`
   и chain id, для которого этот режим разрешён (devnet или testnet).
3. Вариант анклава без SGX. Кандидатов два, выбор — короткой пробой:
   - `outbe-tee-enclave-mock` (feature `mock`): режим разработки, требует
     `--dev-network-binding`;
   - `outbe-tee-enclave-local-e2e` (feature `local-e2e`): боевой протокол
     NodeHost с программным sealing.
   Критерий: работает с немодифицированной нодой и допускает `tee join` после рестарта.
4. Сеть между VM. Вариантов два, выбор — короткой пробой:
   - bridge: у каждой VM свой IP, раскладка портов одна на всех, как и ожидает
     launch bundle;
   - user-mode: проброс портов с хоста, VM видят друг друга через `10.0.2.2`;
     тогда порты p2p разводятся по валидаторам правкой сгенерированных скриптов.
5. Развернуть четыре VM, раздать каждой свой архив.

Готово, когда:

- все четыре ноды производят блоки, высота растёт на каждой;
- TEE DKG завершён, в блоке 1 зарегистрированы четыре анклава и ключ offer;
- оффер отправлен и расшифрован;
- одна VM перезапущена: её анклав пуст, `outbe-cli tee join` возвращает ключ,
  валидатор снова участвует.

## Этап 4. Аттестация dstack в протоколе (правки кода)

Цель: новый режим аттестации, где доказательством служит аттестация dstack
(платформа `sev-snp`), а проверяет её анклав при исполнении блока.

Известные места в коде:

| Что | Где |
|---|---|
| Режим аттестации (сейчас `DcapRequired`, `GramineDirectDev`) | `crates/blockchain/primitives/src/tee_attestation_v1/network.rs` |
| Формат доказательства `AttestationEvidenceV1` | `…/tee_attestation_v1/evidence.rs` |
| Политика и правила измерений `TeePolicyV1` | `…/tee_attestation_v1/policy.rs` |
| Запись политики в genesis | `bin/outbe-chain/src/tee_genesis.rs`, `bin/outbe-genesis-cli/src/attestation.rs` |
| Источник квоты в анклаве (уже внедряется указателем на функцию `quote_generator`) | `bin/outbe-tee-enclave/src/transport/…`, `gramine.rs` |
| Тип среды `AttestationType` и запрет старта без SGX-sealing | `bin/outbe-tee-enclave/src/gramine.rs`, `run.rs`, `initialization/factory.rs` |
| Проверка доказательства внутри анклава | `bin/outbe-tee-enclave/src/dcap_verifier.rs`, `crates/system/tee/src/dcap_v1.rs` |
| Реестр и его интерфейс | `crates/system/teeregistry/`, `contracts/precompiles/src/ITeeRegistryV1.sol` |
| Команда присоединения | `bin/outbe-cli/src/commands/tee/join/` |

Библиотеки dstack для проверки (git-зависимости, закреплённые на коммит):
`sev-snp-qvl` (подпись отчёта и цепочка AMD; при вложенной цепочке сертификатов
не ходит в сеть и не читает время), `dstack-mr` (ожидаемое измерение образа),
`dstack-types` (документ `MrConfigV3` и его хэш в `HOST_DATA`).
Путь TDX из `dstack-attest` не берём: он ходит в сеть и читает системное время.

**Шаг 4.0 — проектная записка на утверждение, до любого кода.** В ней: точные
новые значения перечислений и формат доказательства на проводе, поля правила
измерений, флаги `tee genesis`, влияние на ABI реестра, список зависимостей и их
вес в анклаве, разбор детерминизма, поведение анклава без долговременного
хранения. Это внешняя поверхность протокола, поэтому без утверждения не кодируется.

После утверждения — отдельные изменения, каждое собирается и проходит тесты:

1. среда анклава «dstack»: отчёт через guest agent, ключи только в памяти;
2. новый вид доказательства и его проверка в анклаве;
3. политика, genesis и реестр;
4. путь `tee join` для нового режима.

Отладка — здесь, на `--simulated-tee dstack-amd-sev-snp`; корнем доверия в политике
dev-сети служит тестовый корень симулятора.

Готово, когда: четыре валидатора регистрируются отчётами формата SEV-SNP,
проверенными по политике; регистрация с чужим измерением или чужим `HOST_DATA`
отклоняется (отрицательный тест).

## Этап 5. Настоящее железо AMD

1. BIOS: SMEE, SEV Control, SEV-ES ASID Space Limit, SNP Memory (RMP Table)
   Coverage, SEV-SNP Support.
2. Хост: ядро, QEMU и OVMF с поддержкой SNP. Проверка: `/dev/sev` существует,
   в `dmesg` есть `SEV-SNP enabled`, `kvm_amd/parameters/sev_snp` равно `Y`.
3. `dstackup install --platform amd-sev-snp` с тем же образом, что на этапе 4.
4. Повторить сценарий этапа 4 с боевым корнем AMD в политике.
5. Сертификат процессора (VCEK): либо его отдаёт хост вместе с отчётом, либо
   узел скачивает его заранее и вкладывает в транзакцию регистрации.

Готово, когда: сценарий этапа 4 проходит с отчётами, подписанными процессором.

## Вне этого плана

- raw TCP вместо Noise и слияние анклава с нодой;
- проверка TDX-квот;
- удаление Docker из гостевого образа;
- боевая доставка ключей валидатора в VM;
- разрешение нового образа при остановленной цепи;
- миграция действующей сети с SGX.

## Риски и неизвестные

- Ничто из dstack на этой машине ещё не запускалось; всё выше прочитано в коде
  и документации. Этап 1 существует, чтобы это снять.
- Симулятор SEV-SNP может расходиться с настоящим железом — отсюда этап 5.
- Вес зависимостей `sev-snp-qvl` (в нём есть `tokio` и `reqwest` ради сетевого
  клиента) внутри анклава: возможно, понадобится собирать без сетевой части.
- Как `tee join` ведёт себя, когда у узла есть действующая запись в реестре, а
  анклав стартовал с новыми ключами: в коде есть путь «замещающего кандидата»,
  на этапе 3 проверяется на практике.
- Основные крейты dstack не опубликованы на crates.io, а метаданные лицензии
  расходятся (в `Cargo.toml` MIT, в `LICENSE` Apache-2.0).
- Памяти хоста может не хватить на четыре ноды одновременно с остальной
  нагрузкой; тогда размер VM уменьшается либо этап 3 переносится на AMD-сервер.

## Проверка в целом

- Этап 1: `dstack info <vm>` показывает `Boot Progress: done`; ответ
  `/v1/Attest` принят `dstack-verifier`.
- Этап 2: `systemctl is-active` трёх юнитов внутри VM; содержимое
  `/dstack/persistent` до и после рестарта.
- Этап 3: `eth_blockNumber` на четырёх RPC растёт; в реестре (`0x…EE0A`) четыре
  записи; событие расшифровки оффера; повторный вход после рестарта одной VM.
- Этап 4: `cargo nextest run` по затронутым крейтам, `cargo fmt --all --check`,
  `cargo clippy --all-targets -- -D warnings`; сценарий этапа 3 в новом режиме;
  отрицательный тест на измерение.
- Этап 5: те же сценарии на сервере AMD.
