## Цель

Показать, что один и тот же образ VM с валидатором outbe-chain работает под
self-hosted dstack и на Intel TDX, и на AMD SEV-SNP, по отдельности и в одной
смешанной сети. Защищается память VM. Сборка образа воспроизводима.

## Допущения MVP

1. Диск данных не шифруется; внутри обычный reth.
2. Ключ offer хранится только в памяти VM, ничего не запечатывается (Р30).
   После рестарта VM ключ получается заново через `outbe-cli tee join` (Р26).
3. Риск «все валидаторы потеряли состояние одновременно» не решается.
4. Все программы и скрипты запуска — внутри образа. С диска данных и из
   пользовательской конфигурации читаются только данные.
5. Аппаратные режимы разрешены только для devnet и testnet.

## Зафиксированные решения

Если факт на практике противоречит решению — остановка и доклад, без
самостоятельной замены решения.

1. dstack — только подложка: VMM, гостевая ОС, выдача отчётов. KMS, gateway и
   контракты dstack не используются (подтверждено 2026-11-11: KMS решал задачу
   вне MVP).
2. В образе наши процессы: `outbe-chain`, `outbe-radicle`, анклавный сервис.
   Запуск раннером `bash`.
3. Анклавный сервис — отдельный процесс; канал нода↔сервис не меняется.
4. Закреплённая версия dstack: ветка `next`, коммит
   `c88f60e781a62d542e0843b333f18a48d1458b88`, с патчами из
   `deploy/dstack/patches`.
5. Протокол: решения Р1–Р32 из пяти записок (дополнение 4: Р28–Р32). Крейт `sev` — версия 8.0.0.
6. Смешанная сеть между серверами — открытые порты: RPC и Radicle всем, P2P и
   остальное только адресам валидаторов через firewall хоста. У каждого
   валидатора свой набор портов.

## Ограничения

- **Ветка.** Изменения репозитория — только в ветке `mvp-tdx-dstack`, в worktree
  `~/outbe-chain-mvp-tdx`. В `main` ничего не попадает. Ветку в `~/outbe-chain`
  не переключать.
- **Коммиты.** Commit, push, PR, merge — только по отдельной команде
  пользователя. Без строк об авторстве ассистента.
- **Нагрузка на общий сервер** (`<build-host>`). Тяжёлые задачи — строго по
  одной, с низким приоритетом: `nice -n 19 ionice -c3 … -j 4`.
- **Чужое не трогать.** `/opt/outbe`, CI-раннеры, чужие сессии агентов, чужие
  контейнеры и worktree.
- **Серверы.** AMD: `ubuntu@<amd-host>` (EPYC 7413). Intel:
  `ubuntu@<intel-host>` (Xeon 6527P). Арендованные; BIOS не менять без
  пользователя.
- **Внешние сервисы.** Передача идентификаторов железа наружу (AMD KDS, Intel)
  — только с согласия пользователя. Полученные согласия: VCEK у AMD,
  регистрация платформы у Intel.
- **Безопасность настроек.** Проверку TLS и подобные защиты не отключать.
- **Язык.** Код, комментарии, тесты, сообщения коммитов — на английском. Отчёты
  и записки — на русском.
- **Достоверность.** «Работает» — только с выводом команды, полученным в этом
  исполнении. Прочитанное в коде или документации помечается как
  непроверенное.

### 5. Смешанная сеть

Тот же образ, режим `ConfidentialVmRequired`: два валидатора на сервере Intel,
два на сервере AMD; порты и firewall по решению 6.

Готово, когда: блок 1 зарегистрировал четыре анклава доказательствами двух

### 5а. Неизменяемость образа (добавлено 2026-11-11, подтверждено пользователем)

Итоговые прогоны задач 2, 3 и 5 выполняются на образе `prod` (без SSH и
оболочки) с манифестом без ключа SSH. Наблюдение только снаружи: RPC и
`dstack logs`. Повторный вход после рестарта VM делает скрипт внутри образа.
Прогоны на `dev` с входом по SSH в зачёт не идут.

Отрицательные проверки на железе, обе платформы:

- в VM нельзя зайти;
- исполняемый файл или скрипт, положенный на диск данных, не запускается;
- VM с изменённым образом или манифестом (в том числе `dev` с ключом SSH)
  сеть не принимает: регистрация отклонена, ключ offer не выдан.

### 5б. Оператор не может достать ключ offer у работающей сети (добавлено 2026-11-11)

Защита ключа offer от оператора — цель MVP, а не техдолг (указание
пользователя). Решения Р28–Р32 из дополнения 4 утверждены. ТД-1, ТД-2, ТД-3
закрываются ими и из техдолга убраны.

Готово, когда: Р28–Р32 реализованы; тесты на отказ в выдаче ключа (чужой
корень, чужой манифест, образ вне списка) проходят; на железе VM с изменённым
образом или манифестом ключ не получает; после рестарта VM на диске данных нет
состояния сервиса. Атаку на железе воспроизводить не нужно.

Исключение — основание сети (ТД-5).

Проверки образа r13 (читаются на варианте `dev` той же сборки и по cmdline из
артефактов сборки, без правок кода): опции монтирования диска данных;
`lockdown`, загрузка модулей, kexec; dm-verity и хэш rootfs в cmdline.
Результат записывается в журнал как есть.

## Вне MVP (технический долг)

- ТД-5: при основании сети оператор валидатора-основателя может получить
  ключ offer (церемония не проверяет аппаратные доказательства участников).
  Решение пользователя 2026-11-11: не сейчас; способ исправления записан в
  дополнении 4. Та же проблема в режиме SGX в `main`.
- Расшифровка чужого оффера нодой на частной цепи (утечка содержимого
  офферов, не ключа).
- ТД-6: IMA (контроль и измерение всего исполняемого внутри VM).
- ТД-7: периодическая переаттестация. Регистрация имеет срок, но продление в
  режимах VM не реализовано.
- ТД-8: SEV-SNP — политика не задаёт минимальную версию прошивки (TCB).
- ТД-9: пересчёт ожидаемых измерений из артефактов сборки. Сейчас измерения
  берутся из журнала загрузки VM.
- ТД-11: наблюдаемость образа `prod`. Сейчас снаружи видны консоль VM
  (`dstack logs`), RPC и файлы журнала ноды на диске данных (через
  подключение диска на хосте только на чтение). Нет: журнала сервиса в файле,
  метрик наружу (нода отдаёт их только на `127.0.0.1:9101`), потоковой
  отправки журналов. Варианты: вывод ноды и сервиса на консоль; метрики на
  `0.0.0.0`; отправка журналов по адресу из пользовательской конфигурации;
  общая с хостом папка только для журналов.
- ТД-12: скрипт образа удаляет записи незавершённой попытки входа по именам
  файлов `outbe-tee` (`replacement-*`). Это должно делать само `outbe-cli tee
  join`, когда сервис новый.
- ТД-13: диск данных в VM смонтирован без `noexec`, `nosuid`, `nodev`
  (решение пользователя 2026-11-12: в техдолг; исправление — строка в скрипте
  образа и новый образ).
- ТД-14: тесты `sev_snp_v1.rs` включают два файла с идентификатором чипа
  сервера AMD, которых нет в репозитории (решение пользователя: не
  коммитить; лежат в `~/outbe-amd-fixtures`). На чистом клоне тесты `outbe-tee`
  с признаком `sev-snp` не собираются. Правка файла меняет бинарник сервиса,
  поэтому делается вместе со следующим образом.
- Усиление ядра гостя (`noexec` на диске данных, `lockdown`, запрет загрузки
  модулей и kexec, dm-verity): в MVP только проверяется и докладывается;
  исправление невыполненного — патчем образа, по отдельному решению.
- Продление регистрации, замена и переход измерения в аппаратных режимах.
- Отрицательные тесты на железе (чужой образ или манифест, дамп памяти с
  хоста, сверка расчётного измерения с настоящим) и `tee join` нового узла —
  если не будут сделаны попутно в задачах 2–5.
- Ограничение частоты запросов RPC.
- Отправка оффера (снято пользователем); raw TCP вместо Noise; удаление Docker
  из гостевого образа; боевая доставка ключей; миграция действующей сети с
  SGX; любые действия с testnet и боевыми узлами.

## Обязательные остановки

В любой момент, если:

- факт противоречит зафиксированному решению или допущению MVP;
- требуется изменить протокол сверх Р1–Р32;
- нужно передать наружу идентификаторы железа или секреты сверх уже
  согласованного;
- действие затрагивает чужие процессы или файлы;
- свободного диска на общем сервере меньше 30 ГБ;
- задача не проходит свой критерий после двух разных попыток исправления.

Вне этих точек исполнение не прерывается ради подтверждений.
