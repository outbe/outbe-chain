# Дополнение 4 к проектной записке: оператор не должен достать ключ offer

Дополняет записки Р1–Р27. Статус: **утверждено 2026-11-11** (Р28–Р32: «Да»; атаку на железе не
воспроизводить). Реализация — в ветке `mvp-tdx-dstack`, не закоммичена.

Повод: 2026-11-11 пользователь указал, что защита ключа offer от оператора —
цель MVP, а не техдолг. Память VM защищается только ради этого.

## Что найдено

Сторона выдачи ключа (`bin/outbe-tee-enclave/src/dcap_verifier.rs`,
`build_onboarding_artifact`) доверяет тому, что присылает нода:

1. Политика приходит в запросе. Сервис сверяет запрос только с chain id, хэшем
   genesis и эпохой ключа. Хэша политики в состоянии сервиса нет
   (`EnclaveInitializationManifestV1`).
2. Проверка отчёта SEV-SNP доверяет корневому сертификату из доказательства,
   если его SHA-256 равен хэшу из политики
   (`crates/system/tee/src/sev_snp_v1.rs`, сверка `pinned_ark_sha256`).
3. Правило «выдаю только такому же коду, как я» в режимах VM снято решением
   Р27 и заменено на «допущен политикой».

Нода берёт политику из состояния цепи, а genesis и ключи валидатора лежат на
нешифрованном диске данных. Хэш genesis политику не покрывает.

## Пути оператора к ключу

| № | Путь | Образ `prod` закрывает? |
|---|---|---|
| 1 | Нода получает от оператора genesis с его политикой (свой корень, своё измерение) и его комитетом. Сервис получает ключ через `tee join` в настоящей сети. Затем нода исполняет блок частной цепи с регистрацией «узла» оператора, сервис шифрует ключ на ключ оператора | нет |
| 2 | SEV-SNP: запечатанное состояние на диске читает VM с тем же образом и другим манифестом (ТД-2) | нет |
| 3 | Вход по SSH в образ `dev` | да |
| 4 | Поддельный описатель сети для принимающего сервиса: ключ уходит в измеренную VM в обход реестра (ТД-1) | нет |

Пути 1, 2, 4 выведены из чтения кода, на железе не воспроизводились.
Прежняя формулировка ТД-1 («получить ключ через частную цепь») описывала путь 1,
но приписывала его описателю сети.

Не проверено: закреплён ли корень Intel внутри библиотеки проверки квот
(QVL 1.26). В нашем коде корень Intel сверяется только с хэшем из политики
(`dcap_v1.rs`, `IntelRootMismatch`).

## Принцип исправления

Сервис решает о выдаче ключа только по тому, что измерено процессором или
зашито в его собственный код. Данные от ноды (политика, состояние цепи) для
этого решения не источник доверия. Политика в реестре остаётся — как правило
консенсуса для допуска узла, но не как защита ключа.

## Р28. Корни производителей закреплены в сервисе

- AMD: корневой сертификат из доказательства должен совпадать с одним из
  встроенных в крейт `sev` (Milan, Genoa, Turin). Сверка с хэшем из политики
  остаётся дополнительной.
- Intel: подтвердить тестом, что QVL отклоняет цепочку с чужим корнем. Если не
  отклоняет — закрепить хэш корня Intel в коде сервиса.
- Тестовые корни (симулятор) допускаются только в сборке с тестовым признаком,
  которая в образ не попадает.

Следствие: сеть в симуляторе с аппаратным режимом невозможна. Это уже так (Р20).

## Р29. Правило выдачи ключа: «такой же измеренный, как я»

Заменяет правило из Р27. Сервис выдаёт ключ узлу, если:

1. доказательство проверено по закреплённому корню (Р28);
2. измеряемый манифест получателя тот же, что у выдающего;
3. измерение образа получателя входит в список, записанный в измеряемом
   манифесте выдающего.

Список в манифесте содержит измерения образа для обеих платформ и для каждой
формы VM. Измерения образа известны до написания манифеста, цикла нет: манифест
не содержит собственного хэша.

Пункт 2 внутри одной платформы — равенство `HOST_DATA` (SEV-SNP) или
`MRCONFIGID` (TDX) собственному значению из собственного отчёта. Между
платформами сервис вычисляет ожидаемое значение второй платформы из своего же
документа конфигурации.

Нужно проверить до кода: документ конфигурации dstack (`MrConfigV3`) у VM на TDX
и на SEV-SNP при одном манифесте одинаков. Данные для проверки уже есть в
`~/outbe-tdx-mvp/{amd,intel}-evidence`. Если не одинаков — остановка и доклад.

Следствия:

- политика в реестре должна соответствовать списку в манифесте; иначе узел
  зарегистрируется, но ключ не получит;
- смена образа = новый манифест = новая сеть. Переход между образами в
  работающей сети — вне MVP.

## Р30. В режимах VM состояние сервиса только в памяти

Запечатывание на диск в режимах VM убирается: ключ процессора SEV-SNP и ключ
гостевого агента dstack не используются. После рестарта VM — повторный вход
(Р26). Поле `tee_state` из пользовательской конфигурации убирается.

Закрывает путь 2 и снимает ТД-2 и ТД-3. Соответствует допущению MVP 2.

## Р31. Описатель сети привязан к измеряемому

Вариант А из Р23: хэш описателя сети записан в измеряемом манифесте, сервис
сверяет файл с диска. Закрывает путь 4 и снимает ТД-1.

## Р32. В зачёт идёт только образ `prod`

Измерения образа `dev` в список из Р29 не попадают. Сеть на `dev` — отдельный
манифест и отдельная сеть для отладки.

## Что остаётся открытым

- Расшифровка оффера происходит при исполнении блока. Нода на частной цепи
  может попросить сервис расшифровать чужой оффер. Это не утечка ключа, но
  утечка содержимого офферов. По указанию пользователя оффер не трогаю; пункт
  записан, чтобы не потерялся.
- Атаки на само железо и побочные каналы — вне MVP.

## Проверка (критерий готовности)

На обеих платформах, образ `prod`:

1. Модульные тесты: запрос на выдачу с чужим корнем, с чужим манифестом, с
   измерением вне списка — отклонён; с допустимым узлом другой платформы —
   принят.
2. На железе: VM с изменённым образом или манифестом ключ не получает.
3. На железе: путь 1 воспроизведён целиком (genesis оператора, частная цепь) —
   ключ не выдан.
4. После рестарта VM на диске данных нет состояния сервиса.

## Объём

Сервис (правило выдачи, корни, отказ от запечатывания, сверка описателя),
манифест и скрипты сборки, тесты. Реестр и формат транзакций не меняются.
Новый образ и повтор прогонов TDX, SEV-SNP и смешанной сети.

### ТД-5. Ключ утекает при основании сети (решение пользователя: вариант Б)

Ключ offer рождается в церемонии между сервисами валидаторов-основателей до
блока 1. Ключи участника церемонии заверены только его собственной подписью;
аппаратное доказательство до выдачи частей ключа никто не проверяет, и блок 1
не связывает аттестаты с участниками церемонии. Оператор валидатора-основателя
может пройти церемонию обычной программой и восстановить ключ.

Это исходное устройство протокола: код одинаков в `main` и в режиме SGX.
Вошедших позже валидаторов не касается.

Решение пользователя 2026-11-11: в MVP не исправлять; проблема решаема, способ
понятен. Способ: участник прикладывает аппаратный отчёт, связывающий его ключи
церемонии; сервис проверяет отчёты всех участников по закреплённым корням и по
списку в своём манифесте до выдачи частей. Меняет обмен между нодами и запрос
нода→сервис.

Утверждение MVP после этого: **оператор не может достать ключ у работающей
сети; при основании сети основатели доверяют друг другу.**

### Изменение правила Р28 для режима SGX

Сравнение корня Intel с закреплённым хэшем стоит в общей проверке квот, поэтому
действует и в режиме SGX (`DcapRequired`). Настоящие квоты оно не отклоняет.
