# Что настроить на серверах

Источники команд: `deploy/dstack/README.md`, `deploy/dstack/HARDWARE.md`,
`deploy/dstack/host-setup.sh`. Здесь — полный список того, что реально
потребовалось, с причинами.

Обе машины: Ubuntu 26.04, ядро 7.0, QEMU 10.2.1 из дистрибутива. BIOS на
арендованных серверах не меняли: нужные настройки уже были включены.

## Общее для обоих серверов

| Шаг | Что | Зачем |
|---|---|---|
| Пакеты | `qemu-system-x86 qemu-utils swtpm swtpm-tools libvirt-clients dnsmasq-base jq` | `qemu-utils` — VMM вызывает `qemu-img`; `libvirt-clients` — сетевому помощнику VMM нужен бинарь `virsh` (демон libvirt не нужен) |
| Группа | пользователь в группе `kvm` | доступ к `/dev/kvm` |
| Модуль | `modprobe vhost_vsock` | канал VMM ↔ гость |
| Инструменты dstack | `dstack-vmm`, `dstack-supervisor`, CLI `dstack` в `~/.local/bin` | собираются из той же ревизии dstack |
| `~/.dstack-vmm/vmm.toml` | путь к образам, QEMU, `kms_urls = []`, `gateway_urls = []`, `allowed_bridges = ["obr0"]`, без `[cvm.tee_simulator]` | симулятор нужен только на машине без TEE |
| Сеть VM | мост `obr0` `10.77.0.1/24`, `dnsmasq` только на мосту, помощник `dstack-vmm netd` под root | у каждой VM должен быть свой адрес |
| Запуск VMM | из каталога `~/.dstack-vmm/run` | путь к сокету API относительный |

Всё это делает `host-setup.sh packages | tools | network-up | vmm-start`;
`status` печатает состояние.

Особенности сети VM, найденные в работе:

- Проброс портов QEMU (user-mode) для консенсуса не годится: транспорт
  Commonware принимает входящее соединение, только если адрес источника равен
  зарегистрированному адресу пира. Нужен мост.
- `dnsmasq` запускается с `--dhcp-ignore-clid`: гость при каждой загрузке
  представляется новым client-id и без этой опции получает другой адрес.
- Аренды бессрочные; пул `10.77.0.10–50`. При многократном пересоздании VM
  пул кончается (41 из 41) — аренды надо сбрасывать.
- Мост, DHCP и `netd` не переживают перезагрузку хоста; `network-up` надо
  повторить.
- У VM на мосту нет выхода в интернет. Нода при старте скачивает CRS
  Barretenberg — его раздаёт сервер бандлов (`crs_url`).

## AMD SEV-SNP (EPYC 7413, Milan)

| Шаг | Что |
|---|---|
| BIOS | SMEE, SEV Control, SEV-ES ASID Space Limit, SNP Memory (RMP Table) Coverage, SEV-SNP Support — включены |
| Параметры ядра | **убрать `iommu=pt`**: с ним SNP выключен (`AMD-Vi: SNP: IOMMU disabled or configured in passthrough mode`) |
| `/dev/sev` | правило udev `KERNEL=="sev", GROUP="kvm", MODE="0660"` — иначе устройство доступно только root |
| Проверка | `/dev/sev` есть; `dmesg` содержит `SEV-SNP enabled`; `/sys/module/kvm_amd/parameters/sev_snp` = `Y` |
| VCEK | хост не передаёт гостю таблицу сертификатов; сертификат процессора один раз скачивается из службы AMD (`kdsintf.amd.com/vcek/v1/Milan/<chip id>?blSPL…`) и кладётся в бандл (`SNP_VCEK_FILE`) |

Запрос VCEK передаёт AMD идентификатор чипа. У каждого процессора свой VCEK;
при обновлении прошивки (смене версии TCB) нужен новый.

Факты платформы: прошивка SEV-SNP API 1.58, отчёт версии 5, VMPL 0, подпись
VCEK, четыре версии TCB равны.

## Intel TDX (Xeon 6527P)

| Шаг | Что |
|---|---|
| BIOS | TME, TME-MT, TDX, SEAM loader, SGX — включены. SGX нужен, потому что служба, подписывающая квоты TDX, работает в анклаве SGX |
| Параметры ядра | `nohibernate kvm_intel.tdx=1` — без них модуль TDX не поднимается |
| Репозиторий | Intel SGX для выпуска Ubuntu |
| Пакеты Intel | `tdx-qgs`, `libsgx-dcap-default-qpl`, `sgx-ra-service`, `sgx-pck-id-retrieval-tool`, `sgx-dcap-pccs` (1.27.101.1) |
| QGS | `/etc/qgs.conf`: `port = 4050` |
| Группы | пользователь в `kvm` и `sgx` |
| PCCS | локальный, на `localhost:8081`; нужен ключ API Intel; собственный CA добавлен в системное хранилище, проверка сертификата не отключалась |
| Регистрация платформы | `PCKIDRetrievalTool -url https://localhost:8081` → «Registration status has been set to completed» |
| Проверка | `dmesg`: `virt/tdx: module initialized`; `/dev/sgx_enclave`, `/dev/sgx_provision`; `qgsd` и `pccs` активны; `/sys/module/kvm_intel/parameters/tdx` = `Y` |
| Обеспечение (collateral) | выгружается из PCCS в `collateral.json` и кладётся в бандл (`TDX_COLLATERAL_FILE`) |

Регистрация платформы передаёт Intel идентификаторы железа. Автоматическая
регистрация в BIOS была выключена («SGX Auto MP Registration is disabled»),
поэтому она делалась с хоста.

Без PCCS и регистрации гость зависает на этапе «requesting app keys»:
`tdx_guest: GetQuote request timedout`.

Обеспечение имеет срок: выгруженное 2026-11-11 действует до 2026-12-11. После
этого новые регистрации с этим файлом проходить не будут; его надо обновлять.

Факты платформы: квота версии 4, тип TEE 0x81, данные сертификации типа 5,
FMSPC `70A06D070000`, ядро отдаёт 307 лишних байт после подписи (нода их
обрезает).

## Сеть между серверами (смешанная сеть)

Команда: `host-setup.sh expose <публичный адрес> <адреса пиров> <vm-ip>:<сдвиг> …`

| Порт VM со сдвигом N | Открыт |
|---|---|
| RPC, внешний порт 8545+N | всем |
| Radicle 8776+N | всем |
| консенсус 30400+N, reth 30303+N, discv5 31303+N | только перечисленным адресам пиров |

Два валидатора за одним публичным адресом получают разные сдвиги портов
(`port_offset` в пользовательской конфигурации и `PORT_OFFSETS` в
`make-bundles.sh`). Правила `expose` не переживают перезагрузку.

## Входной firewall хоста

`host-setup.sh firewall` ставит таблицу nftables `outbe_host_fw`: на вход
самого хоста — только SSH и мост VM. Отдельная таблица, чужие правила не
затрагивает; служба `outbe-host-firewall` загружает её после перезагрузки.
Порты валидаторов — не порты хоста: `expose` пересылает их в VM, и входная
цепочка их не касается. `firewall-try` включает правила на две минуты для
проверки, что SSH не отрезан.

## Порядок запуска сети в аппаратном режиме

1. Собрать образ (или скопировать готовый), установить вариант `prod` в
   `~/.dstack-vmm/image/`.
2. Снять измерения образа с любой VM этого образа и этой формы (3 vCPU, 5 ГиБ):
   - TDX — страница гостевого агента, порт 8090, `/prpc/Info`, поле `tcb_info`
     (`MRTD`, `RTMR0`–`RTMR2`);
   - SEV-SNP — отчёт внутри сертификата VM с той же страницы, смещение `0x90`.
3. Сгенерировать ключи валидаторов (`outbe-keygen validator`).
4. `make-bundles.sh` с `TEE_MODE=tdx | sev-snp | mixed` и измерениями. Скрипт
   пишет бандлы, genesis с политикой и манифест сети `<net>/app-compose.json`.
5. Раздать бандлы по HTTP с адреса моста.
6. Создать VM: `dstack deploy --image … --compose <net>/app-compose.json
   --user-config … --vcpu 3 --memory 5G --disk 40G --net bridge`,
   `"tee_mode": "confidential-vm"`.
7. Все четыре ноды должны подняться в пределах 120 секунд: основатели вместе
   проводят церемонию создания ключа.
8. Проверка снаружи: `outbe_consensusStatus` на порту 8545 — `mode: signer`,
   `enclave.state: ready`, `offerKeyReady: true`.

Измерения зависят от образа и формы VM, но не от манифеста. Поэтому шаг 2
делается на пробной VM с любым манифестом, а манифест сети создаётся после.
Зависимость от формы VM (число процессоров, память) не измерялась: все
прогоны шли с одной формой.

## Перезапуск валидатора

1. `dstack update-user-config` — задать `upstream_url` (RPC живого узла).
2. `dstack stop`, `dstack start`.
3. Скрипт образа сам выполняет вход и запускает ноду. Вмешательство в VM не
   требуется и невозможно.

## Что оператор видит без входа в VM

| Канал | Что видно |
|---|---|
| RPC, порт 8545 | данные цепи, режим консенсуса, состояние сервиса |
| `dstack logs <vm>` | консоль VM: загрузка и старт юнитов; вывода наших сервисов там нет |
| порт 8090 VM | хэш образа, хэш манифеста, измерения |
| диск данных, подключённый на хосте только на чтение (`qemu-nbd -r`) | журналы ноды, данные цепи |

Причину отказа сервиса на образе `prod` снаружи узнать нельзя — это ТД-11.

## Состояние серверов на 2026-11-12

- На обоих работает смешанная сеть r16 (2 VM на Intel, 2 на AMD), правила
  `expose` и входной firewall. Оставлена по решению владельца.
- На дисках валидаторов 1 и 3 этой сети лежат файлы, подложенные для проверки.
- На сервере Intel установлены PCCS и QGS; в PCCS лежит ключ API Intel.
