# Один числовой агрегат uint256 через Pedersen VSS: проверка конструкции

Дата проверки источников: 2026-09-11. Статус: арифметическая конструкция проверена отдельным [компонентным прототипом](measurements/wide-vss/README.md); сетевой протокол и связанный admission proof не готовы. SEAL и TEE в этом варианте отсутствуют. Здесь рассматривается получение суммы для **уже определённого множества Tribute**; позднее распределение по лигам — отдельный вопрос [хранения и выбора множества](STORAGE_AND_AGGREGATE_PROTOCOL.md).

**Вывод:** группа с достаточно большим порядком позволяет открыть один `S = Σ nominal6`, без открытия четырёх сумм частей числа. Для максимум `10⁹` входов uint256 подходит порядок группы P-384. VSS распределяет сам nominal и его blinding; ключ расшифрования и DKG для этой арифметики не нужны. Но пользовательский proof должен быть криптографически связан с этим же commitment.

## 1. Поле и генераторы

Обозначим **q — порядок группы**, а p — модуль поля координат кривой. Все значения, blindings, коэффициенты полиномов и интерполяция VSS работают в `F_q`, не в `F_p`. Для P-384 cofactor равен 1, порядок прост и имеет вид:

```text
q = 0xffffffffffffffffffffffffffffffffffffffffffffffffc7634d81f4372ddf581a0db248b0a77aecec196accc52973
```

Параметры подтверждены [NIST SP 800-186, §3.2.1.4](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-186.pdf). Выбор стандартной кривой не означает, что NIST сертифицирует предлагаемый протокол VSS.

Наш расчёт точными целыми:

```text
0 ≤ nominal6_i ≤ 2²⁵⁶ − 1
N ≤ 10⁹
Σ nominal6_i ≤ 10⁹ × (2²⁵⁶ − 1) < 2²⁸⁶ < q
```

Следовательно, честно ограниченная сумма не оборачивается по модулю q. Сам агрегат может превышать uint256: для него нужен широкий тип либо отдельное экономическое правило ограничения общего объёма. Проверка одного commitment такого ограничения не доказывает.

Предложение для параметров: стандартный base point `G`; независимый `H = hash_to_curve(protocol_label || chain_id || version || counter, DST)` по `P384_XMD:SHA-384_SSWU_RO_`, с фиксированным правилом повторения при identity. Все участники вычисляют одинаковый H. RFC определяет suite и требует domain separation; конкретные label/DST здесь — проектируемый формат. Нельзя брать `H = hash_to_scalar(label) × G`: тогда всем известен `log_G(H)`, и binding commitment теряется. [RFC 9380, §§3.1, 8.3](https://www.rfc-editor.org/rfc/rfc9380.html#section-8.3).

## 2. Кто создаёт и проверяет доли

У пользователя есть `a = nominal6` и случайный независимый `r ∈ F_q`. Он создаёт `C = aG + rH`. При пороге восстановления t он выбирает два полинома степени не выше `t−1`:

```text
A(X) = a + α₁X + … + αₜ₋₁Xᵗ⁻¹
B(X) = r + β₁X + … + βₜ₋₁Xᵗ⁻¹
V_k  = α_k G + β_k H,       V_0 = C
share_j = (A(x_j), B(x_j))  — только получателю j
```

Координаты участников `x_j` публичны, различны и ненулевые. Пользователь публикует `V_0…V_t−1`, отправляет каждой ноде только её пару долей по защищённому аутентифицированному каналу. Получатель проверяет:

```text
A(x_j)G + B(x_j)H == Σ_k x_j^k V_k
```

Это аддитивная запись Pedersen VSS. При честном распределении меньше t участников не получают информации о секрете; корректность связывания опирается на сложность дискретного логарифма и неизвестность связи G/H. [Pedersen, CRYPTO 1991](https://cgi.di.uoa.gr/~aggelos/crypto/page8/assets/Pedersen-VSS.PDF).

**Нельзя заменить эти commitments на Feldman `aG` для nominal.** Такая точка позволяет проверить предположение о сумме перебором кандидатов; Pedersen добавляет случайное маскирование. [Feldman, FOCS 1987](https://www.cs.umd.edu/~gasarch/TOPICS/secretsharing/feldmanVSS.pdf). Знание одного blinding без самой суммы также не превращает commitment в обычный расшифровываемый ciphertext.

## 3. Кто получает общую сумму

Следующие формулы — наша композиция VSS для утверждённого набора I. Ноды должны согласовать одинаковые `day`, `set_root`, count и версию параметров; одинаковое имя дня без одинакового набора недостаточно.

Каждый участник j локально складывает только свои проверенные доли:

```text
U_j = Σ_i∈I A_i(x_j)       W_j = Σ_i∈I B_i(x_j)
VΣ_k = Σ_i∈I V_i,k        CΣ = VΣ_0 = Σ_i∈I C_i
```

До закрытия ни один отдельный участник не вычисляет S. После фиксации набора публикуются t корректных **агрегатных** пар `(U_j, W_j)` с идентификаторами и привязкой к `set_root`. Любой валидатор проверяет каждую пару по `VΣ_k` и вычисляет:

```text
λ_j = Π_m∈Q,m≠j x_m / (x_m − x_j) mod q
S   = Σ_j∈Q λ_j U_j mod q
R   = Σ_j∈Q λ_j W_j mod q
check: SG + RH == CΣ
```

Здесь Q — согласованный набор t публикующих участников. Результат — один целый S и агрегатный blinding R. Публикуемые доли дополнительно позволяют восстановить случайные коэффициенты двух агрегатных полиномов, **но не создают выходы в виде отдельных limb totals**. Рандомизация полиномов не кодирует дополнительных денежных величин. Индивидуальные `(a_i,r_i)` не публикуются. При корректном proof диапазонов и ограничении N канонический S совпадает с обычной целочисленной суммой, а не только её остатком modulo q.

Можно хранить в итоговом state только `(S,R,CΣ,set_root)` после проверки; размер полного проверяемого transcript больше. Если публичный вывод должен быть буквально только S без R, нужна дополнительная proof-обёртка — для заявленной приватности индивидуальных сумм R сам по себе не требует такой обёртки.

## 4. Смена состава без восстановления S

Зафиксирован старый агрегатный checkpoint и набор Q из t старых участников. Каждый старый участник j знает только `(U_j,W_j)` и создаёт новые полиномы `P_j,Q_j` степени `t_new−1` с константами `λ_j U_j, λ_j W_j`. Новым участникам передаются пары вычислений этих полиномов, а публично — coefficient commitments `E_j,k`.

Новый участник проверяет **две связи**:

```text
E_j,0 == λ_j × Σ_k x_j^k VΣ_k           — продолжен старый секрет
P_j(y_l)G + Q_j(y_l)H == Σ_k y_l^k E_j,k — новая доля корректна
```

Он складывает принятые пары по всем j из одного Q. Получаются новые доли тех же `(S,R)`, и `Σ_j E_j,0 == CΣ`. Ни на одном шаге S не собирается в открытом виде. Только после завершённой передачи и подтверждения нового checkpoint можно удалить старые доли.

Это описанная здесь адаптация линейного перераспределения к паре Pedersen-полиномов. Проверять только новые доли недостаточно — обязательна связь с прежним commitment. Именно эту проблему устанавливает [Wong–Wang–Wing, CMU-CS-02-114, §§4–5](https://www.cs.columbia.edu/~wing/publications/CMU-CS-02-114.pdf). Их конкретная теорема предполагает честность всех новых получателей; она **не является готовым доказательством** устойчивости нашей композиции к злонамеренным новым валидаторам.

Ротация и proactive refresh требуют отдельного протокола жалоб, общего Q, таймаутов, повторного выбора Q, подтверждения доставки и удаления старых секретов. Условие «меньше t скомпрометированных одновременно» без ограничений на переход эпох и стирание старых данных недостаточно. [Herzberg–Jarecki–Krawczyk–Yung, CRYPTO 1995](https://www.cs.cornell.edu/courses/cs754/2001fa/339.PDF).

## 5. Что обязательно до принятия Tribute

Это требования к нашей композиции, а не свойства, которые одна проверка VSS обеспечивает автоматически:

- ZK-proof знания opening C и `0 ≤ a ≤ 2²⁵⁶−1`; при требовании положительного Tribute — `a > 0`.
- Доказательство, что a — ровно результат разрешённого источника/issuance; proof связан с **тем же** `V_0=C`, владельцем, днём, offer ID, nonce и chain ID.
- Одинаковые публичные coefficient commitments для всех участников, корректное декодирование точек и канонические scalars. Нельзя принимать альтернативные наборы от одного dealer.
- Уникальность учтённого Tribute и ограничение N. Отрицательные значения, представленные как `q−x`, должны отвергаться range-proof.
- Гарантированная доступность необходимого числа долей. Обычная Pedersen VSS позволяет получателю проверить **свою** долю; публичные commitments сами не доказывают, что все доли были доставлены.

При максимум f злонамеренных участниках нужны `f < t` для приватности и минимум t отвечающих владельцев корректных долей для восстановления. Чтобы **одни signed receipts** гарантировали t честных держателей при максимум f лживых/отказывающихся подписантах, нужно не меньше `t+f` receipts. Например, для `n=16,t=11,f=5` нужны все 16, а 11 недостаточно. Это арифметическое условие доступности для простого варианта; для меньшего числа receipts нужен доказанный share-repair/dispersal протокол, а не переименование threshold certificate.

Исследовательский профиль `n=16,f=5,t=6` снижает это требование до 11 receipts; `n=128,f=42,t=43` — до 85. Это компромисс порога приватности и доступности, а не заимствование порога подписи из consensus. Receipt о хранении собственной расшифрованной доли и DA certificate о доступности **полного зашифрованного вектора** — разные модели: во второй нужны доступность ciphertext, ключи получателей, корректность шифрования и отдельный способ получения необходимых долей.

Для одного накопителя важно, чтобы каждый считающий его участник имел долю **каждого** принятого входа. Разные достаточные наборы получателей для разных Tribute ещё не гарантируют общий достаточный набор держателей итоговых долей. Восстановление отсутствующих долей должно произойти до удаления исходных данных либо admission должен поддерживать общий согласованный набор получателей.

Комитет из t сговорившихся держателей может раскрыть индивидуальные входы, пока индивидуальные доли сохранены, или досрочно открыть имеющийся агрегат. VSS не задаёт криптографическую политику «разрешено открывать только сумму в указанное время». Защита предполагает порог честности, регламент handoff и жизненного цикла секретных данных; расшифровывающий DKG-ключ здесь ничего автоматически не исправляет.

## 6. Нерешённая связь с пользовательскими proofs

Использованная ранее библиотека `bulletproofs 5.0.0` принимает `RistrettoPoint` в `PedersenGens` и возвращает Ristretto commitments. Сменяемые базы в её API — **не сменяемая кривая**. [Официальный API PedersenGens](https://docs.rs/bulletproofs/5.0.0/bulletproofs/struct.PedersenGens.html).

Следовательно, прежний proof для четырёх Ristretto limbs не доказывает корректность `C_P384(a,r)`. Требуется один из двух конкретных следующих результатов:

1. Proof диапазонов и экономических связей в той же группе P-384, с проверенной реализацией; либо
2. Proof равенства **одного ограниченного целого** между P-384 commitment и четырьмя Ristretto limb commitments, включая все ограничения против неоднозначности разных модулей.

В этой заметке такой proof не реализован и его время/размер не измерены. Нельзя складывать прежнее время Ristretto-proof и новое время P-384 VSS и выдавать сумму за готовую end-to-end проверку.

При принятых точных формулах `g18=a6·f6·10⁶`, `cost18=a6·f6·p6` обычная нода может вывести `C_g=(f6·10⁶)C_a` и `C_cost=(f6·p6)C_a` без знания a. Их blindings масштабируются так же; пользователь может затем сделать fresh reblinding и proof балансового перехода. Хранить эти точки заранее в Nod необязательно. Но отсутствие wrap для **суммы nominal** не доказывает отсутствие wrap в **произведениях**: границы g/c и целочисленных промежуточных результатов надо проверять отдельно.

## 7. Объём чистых криптографических данных

Ниже наш расчёт, не сетевой benchmark. P-384 scalar занимает 48 B; обычная ненулевая точка в compressed SEC1 — 49 B. Для формата state можно зарезервировать фиксированные 49 B и для identity. [SEC 1 v2, §2.3.3](https://www.secg.org/sec1-v2.pdf).

| Данные | Формула | 16 участников, t=11 | 128 участников, t=86 |
|---|---:|---:|---:|
| Секретная пара одному получателю | 2×48 B | 96 B | 96 B |
| Пары всем получателям одного Tribute | 96n | 1,536 B | 12,288 B |
| Полный набор polynomial commitments | 49t | 539 B | 4,214 B |
| Из них уже существующий C(nominal) | 49 B | 49 B | 49 B |
| Частный state одного фиксированного агрегата у одной ноды | 96 B | 96 B | 96 B |
| t пар для публичной проверки открытия | 96t | 1,056 B | 8,256 B |
| Итоговые S и R в двух scalar slots | 96 B | 96 B | 96 B |

Таблица не включает proof, подписи, индексы, transport encryption, receipts, roots, историю и replication. Handoff одного агрегата по описанной конструкции передаёт `96·t_old·n_new` приватных байт и `49·t_old·t_new` публичных байт. Это **O(число нужных агрегатов)**, если индивидуальные данные больше не нужны. Если лига выбирается позднее, сохранение одной пары на Tribute стоит 96 GB на получателя при миллиарде Tribute — плюс индекс и дисковый overhead. Одно маленькое накопленное S не восстанавливает поздние разбиения по лигам.

Компонент P-384 `create → verify → aggregate → reshare → open` теперь выполнен: [код и результаты](measurements/wide-vss/README.md). Следующий криптографический этап — выбранный proof связи с входом. До него проверена конструкция числового агрегата, но не его сквозная защита от злонамеренного пользователя.
