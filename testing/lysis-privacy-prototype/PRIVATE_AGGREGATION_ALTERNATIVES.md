# Private aggregation: альтернативы SEAL и commitment-only схемам

Первичные источники проверены 2026-09-10. Условия: 1 млрд Tribute за 50 часов; каждый amount полный uint256; точная сумма до 286 бит; владелец уходит после проверенной загрузки; комитет меняется примерно каждый час; eligible-набор определяется позднее в Lysis. Prio/VDAF исследуются отдельно. Новых замеров нет.

Нужны в среднем 5556 загрузок/с. Максимальная сумма `10^9·(2^256−1) < 2^286`. Приведённые ниже размеры не включают доказательства подлинности Tribute, envelope, индексы и репликацию.

## Threshold Paillier / Damgård–Jurik

Сообщение в Z_N шифруется одним элементом Z_(N²); произведение ciphertexts шифрует сумму. Пороговое расшифрование использует проверяемые частичные результаты, без восстановления полного ключа. [Damgård, Jurik, Nielsen, §§3, 5.1](https://people.csail.mit.edu/rivest/voting/papers/DamgardJurikNielsen-AGeneralizationOfPailliersPublicKeySystemWithApplicationsToElectronicVoting.pdf).

**Вывод для задачи:** владелец загружает ciphertext один раз; любой окончательный subset под тем же публичным ключом можно агрегировать позднее. `N > 10^9·(2^256−1)` исключает переполнение суммы.

**Оценка формата:** при условном 3072-битном N ciphertext занимает 768 байт; миллиард — 768 GB, средний поток — 4,27 MB/s. Это не benchmark и не окончательный выбор параметров безопасности. Range proof для uint256 и proof связи с настоящим Tribute необходимы отдельно; их полный размер здесь не установлен.

Часовая ротация требует сохранить публичный ключ и безопасно передать секретные доли либо сохранить старый комитет до Lysis. Новая независимая пара ключей не расшифровывает старые записи. Готовность hour-by-hour handoff для Outbe этим источником не доказана. Пороговый сговор способен расшифровать индивидуальный ciphertext.

## Threshold HSM-CL

Работа 2024 года даёт DKG и threshold decryption для аддитивного шифрования на class groups. Ciphertext состоит из двух элементов группы, сообщение принадлежит F_q; специальный CLSolve извлекает число без огромного дискретного логарифма обычного exponential ElGamal. [Braun et al., §§2, 5–6](https://eprint.iacr.org/2024/717.pdf).

Это второй кандидат для offline owner и late subset. Нужен q выше максимальной 286-битной суммы либо корректное разбиение; конфигурация для 256-битных ECDSA scalars недостаточна автоматически. Авторы измеряли DKG/decryption статического протокола, не миллиард scalar-reports с proof входа. Размер сериализации для наших параметров и hour-by-hour handoff остаются неподтверждёнными. [Там же, §8](https://eprint.iacr.org/2024/717.pdf).

## Joye–Libert / private stream aggregation

Joye–Libert снимает ограничение маленького plaintext у Shi2011: `c_i=(1+x_iN)·H(t)^s_i mod N²`. Ключ агрегатора соответствует сумме ключей участников; он раскрывает сумму самостоятельно после однократных сообщений клиентов. Размер ciphertext снова 2·bitlen(N), то есть условные 768 байт. [Joye–Libert, §§3–4](https://ifca.ai/pub/fc13/78590108.pdf).

Исходная модель допускает одно значение участника за период и cancellation для настроенного набора ключей. Произвольное позднее исключение записей уже не соответствует ключу агрегатора. Fault tolerance и dynamic joins/leaves авторы отделяют как дополнительные механизмы; их вариант не поддерживает weighted sums. [Там же, §1 и §3.1](https://ifca.ai/pub/fc13/78590108.pdf).

**Вердикт:** без дополнительного протокола не подходит для неизвестного заранее eligible-набора; название PSA не решает поздний subset, ротацию и proof истинности входа.

## Flamingo

Обычный клиент отправляет masked vector один раз и уходит. Далее взаимодействуют сервер и decryptors. Есть proactive transfer долей SK новому набору decryptors каждые R раундов: это настоящий положительный пример ротации. [Ma et al., §IV, Appendix B-D](https://arxiv.org/html/2308.09883v1).

Но заранее известны набор кандидатов S_t и граф парных масок. Late eligibility требует сохранения предусмотренных графом гарантий: изолированная честная вершина может раскрыться. Один scalar на 288 бит можно представить 36 байтами, но это лишь masked-часть. Дополнительно нужны шифрования seeds/shares и подписи. Авторы указывают 64 байта на отдельный seed-ciphertext; пример для 1024 клиентов требует минимум 41 соседа при указанных вероятностях, то есть только такие ciphertexts уже дают `41×64=2624` байта. [Там же, §§IV-A, VII, Appendix C](https://arxiv.org/html/2308.09883v1).

**Вердикт:** полезный протокол одноразовой загрузки и ротации, но опубликованный FL-выигрыш нельзя выдавать за компактный uint256-report.

## Lighthouse — USENIX Security 2026

One-shot clients, batched threshold encryption и SNARK допустимости раскрываемых масок снижают нагрузку комитета. O(1) относится к комитету статического варианта; динамическое расширение требует работы каждого decryptor пропорционально новым клиентам. [Garg et al., §§1.1, 4–5](https://www.usenix.org/system/files/usenixsecurity26-garg-sanjam.pdf).

Опубликованный замер: 1024 клиента, 60 decryptors, векторы 16K×32 бит; client report 70,76 KB, server send 68,40 KB с Groth16, decryptor send 0,14 KB. Это не размеры для одного uint256; scalar-report с proof подлинности Tribute ещё надо измерить. SNARK допустимости статусов не доказывает автоматически экономическую корректность входа. [Там же, §6, таблица 3](https://www.usenix.org/system/files/usenixsecurity26-garg-sanjam.pdf).

Статический вариант сохраняет графовые ограничения. В динамическом маски связаны с индивидуальными ключами членов комитета: перенести общий threshold-ключ недостаточно, чтобы объяснить судьбу всех масок после ухода старого комитета. Полный часовой handoff здесь не подтверждён; основное доказательство использует static corruption. Это наиболее актуальный комитетный кандидат для дальнейшего прототипа, но не завершённое решение жизненного цикла Outbe.

## Что проверять дальше

Paillier — понятная исходная точка для измерения полного scalar-report, Lighthouse — кандидат для снижения затрат комитета, CL — дополнительный вариант. Нельзя объявить победителя по размеру только masked value или raw ciphertext.

Нужен общий тест: полный uint256, 286-битная сумма, исключения после загрузки, proof связи с настоящим Tribute, часовая смена/отказ комитета без владельца, проверка одного разрешённого раскрытия. Для Paillier/CL сохранять предполагается ciphertexts и публичный ключ, переносить — ключевое состояние; конкретный безопасный handoff ещё надо реализовать. Для динамического Lighthouse отдельно требуется сохранять способность работать с масками уходящих членов комитета. Правила против singleton/differencing раскрытий остаются требованиями приложения.
