# Flamingo и Lighthouse для Tribute → Lysis → Nod

Проверка: 2026-09-10. Это внешний аудит применимости, без изменения Outbe. Фактические формулы Lysis исследуются отдельно. Исходные требования: миллиард самостоятельных отчётов за 50 часов, полный uint256, числовой итог до 286 бит, однократная загрузка владельцем, поздняя eligibility/группировка и замена комитета примерно каждый час. Ни один опубликованный benchmark ниже не измеряет этот сценарий.

**Вывод:** оба протокола полезны как механизм получения агрегата. Flamingo в исходном виде не закрывает поток неизвестных заранее участников и перенос незавершённого раунда на новый комитет. Статический Lighthouse лучше упаковывает секреты для переноса общего ключа, но требует заранее определённого набора участников. Его динамическое расширение вновь связывает маски с индивидуальными ключами комитета. Это конкретные задачи адаптации, а не доказательство невозможности.

## Проверенные свойства первичных статей

**Flamingo.** Обычный клиент после report уходит; сервер и decryptors завершают cross-check/reconstruction. В модели противник malicious, но **static**. Строгое условие основного анализа — `2δ_D+η_D<1/3`; рассматриваются также параметры corruption/dropout клиентов. Input correctness исключена из задачи. В report входят masked vector, L индивидуально зашифрованных долей self-mask и шифротексты pairwise seeds под общим PK. Передача общего SK между комитетами описана **между раундами**; это не передача всех транспортных ключей и незавершённых входов. [Статья, §§II-C–D, IV-D–F, V, Appendix B-D](https://arxiv.org/html/2308.09883v1).

**Lighthouse.** Основная модель также static malicious; требуется ограничить corruption/dropout клиентов и decryptors. Оба типа seed шифруются через общий TB-IB-KEM. Комитет разрешает один согласованный status digest; SNARK проверяет его допустимость относительно графа. Input poisoning вне охвата; malicious server может вызвать abort. O(1) относится к комитету статического варианта. Динамическое расширение связывает новых клиентов с индивидуальными ключами членов комитета и добавляет им работу пропорционально новым клиентам. [Статья, §§3–5](https://www.usenix.org/system/files/usenixsecurity26-garg-sanjam.pdf).

Далее — наши выводы и предлагаемые адаптации к условиям Outbe, а не свойства, доказанные авторами для блокчейна.

## Где эти протоколы стоят в экономическом цикле

Они могут дать Lysis точные числовые `sumNominal` по утверждённым группам. После этого можно считать публичные коэффициенты и резерв. Они сами не производят скрытые индивидуальные `floor`, не формируют доказательство правильного Nod и не удостоверяют Tribute Offer.

Следовательно, для цикла нужны три разных утверждения:

1. **Вход:** загруженное закрытое число соответствует разрешённому Tribute, находится в uint256 и не заменено между representations.
2. **Агрегация:** числовой результат соответствует ровно утверждённому eligible-набору, без пропусков, повторов и добавления чужих записей.
3. **Выход:** приватное право Nod и его погашение соответствуют этому Tribute и окончательным коэффициентам; nullifier запрещает повторное получение.

Подпись комитета под digest и graph-status SNARK не заменяют все три утверждения. Для публичной проверки сети понадобится отдельная связка proof/state roots. Можно добавить SNARK, но его схема, witness, размер и proving cost входят в стоимость решения.

## Поток за 50 часов и поздние группы

В исходном Flamingo и статическом Lighthouse клиент должен знать кандидатов/соседей до отправки масок. Зарегистрированные владельцы и заранее определённый cohort допустимы, но миллиард произвольных report IDs, появляющихся позже, нельзя без изменения протокола считать заранее известными вершинами. Несколько Tribute одного владельца также требуют самостоятельных nonce/идентификаторов масок; повторять один mask для разных amount нельзя.

Динамический Lighthouse снимает зависимость от будущих соседей: новый клиент использует известный комитет. Это наиболее подходящая часть для независимых arrivals. Но остаётся вопрос ротации индивидуальных ключей, рассмотренный ниже.

### Почему нельзя повторить один набор ciphertexts по каждой лиге

Для первой группы нельзя просто разрешить `A online / остальные offline`, а затем для второй — поменять статусы тех же записей в том же раунде. Первый проход раскрывает один вид масок, второй — другой. Их совместное знание может снять защиту индивидуального входа. Именно поэтому протокол ограничивает разрешённый digest одного раунда.

Практические направления адаптации:

- **Группирующий ключ уже известен при загрузке:** делать отдельные logical rounds для `(day, currency, league, …)`, с независимыми mask domains; поздняя eligibility остаётся единственным финальным исключением внутри группы. Это требует подтверждения, что ключ группы не изменится.
- **Группа действительно определяется позже:** нужен один окончательный partition manifest, а не серия независимых subset-запросов. Возможная конструкция разрешает раскрыть маски рёбер между группами, сохраняет маски внутри каждой группы и проверяет условия приватности каждой группы. Это гипотеза нового протокола; текущая one-of-two схема Lighthouse такого multi-label правила автоматически не доказывает.
- **Динамические client-to-committee маски:** комитет мог бы складывать свои маски по поздно известным public grouping keys. Но он должен сохранить способность вывести каждую нужную маску и доказать соответствие каноническому набору. Эта обязанность переходит через все смены комитета.

Если partial group sums раскрываются каждый час или на каждом work shard, это дополнительные раскрытия, а не только удобная реализация финального итога.

## 256 записей: вычислительный batch и группа приватности различаются

256 не является ни автоматически безопасным, ни автоматически слишком малым размером. Если атакующий знает 255 входов, точная сумма раскрывает оставшийся. Миллион записей от того же атакующего не исправляет проблему. Предположение статьи о доле честных **клиентов** нельзя заменить числом Tribute: один участник может отправить много записей.

Поэтому work shard 256 разумно оставить единицей исполнения. Его итог можно передавать дальше закрыто, а публично раскрывать только окончательные экономически необходимые суммы. При делении этих 256 по нескольким лигам настоящая группа приватности становится ещё меньше. Нужны политика допустимых раскрытий, анализ известных атакующему вкладов и модель admission/Sybil.

Для масштаба важна общая вероятность отказа: миллиард записей — примерно 3,91 млн batches по 256. Если условно обещать failure probability 10^-6 на batch, простая union bound уже не даёт полезной общей гарантии. Это арифметический пример, не оценка действительной ошибки Flamingo.

## Можно ли держать один logical round 50 часов и сделать 50 reshare

**Алгебраически сохранять один PK и обновлять его shares можно рассматривать как направление.** Но elapsed time и слово reshare не доказывают сохранение нужного состояния.

| Состояние | Flamingo | Статический Lighthouse | Динамический Lighthouse |
|---|---|---|---|
| Общий threshold secret | Передаётся между комитетами | Его shares потенциально можно обновлять с сохранением PK | То же для recovery-слоя |
| Self-mask | L shares адресованы индивидуальным decryptors | Шифруется через общий TB-KEM | Зависит от client-to-committee масок |
| Зависимость от индивидуальных ключей старого комитета | Есть для SymAuthEnc self-shares | Для этих TB-KEM seed-ciphertexts нет | Есть для pairwise mask derivation |
| Что недостаточно передать | Только общий SK | Только SK без журнала разрешений и необходимых данных | Только recovery SK |

Конкретно в Flamingo новый decryptor не расшифрует `SymAuthEnc(k_i,old, m_i,old)` своей новой транспортной парой. Варианты: старый комитет доживает до завершения; каждый self-mask reshared до ухода; либо self-mask тоже шифруется общим threshold PK. Последнее — содержательная адаптация, напоминающая упаковку Lighthouse, а не бесплатная смена конфигурации.

В динамическом Lighthouse маска вычисляется из DH-секрета с конкретным старым членом комитета. Передача BTE shares не передаёт этот DH-секрет. Нужно выбрать, сохраняются ли старые эпохальные ключи, передаются ли они безопасным отдельным протоколом, либо заранее переводится необходимое mask-состояние в иную разделённую форму. После поздней фильтрации заранее посчитанной общей суммы масок может быть недостаточно.

Для всех вариантов надо переносить **журнал разрешений**: новый комитет не должен разрешить второй конфликтующий digest старого logical round. Нужны связь с finality, защита от rollback/replay, совместимость индексов shares и erasure старого состояния. Static-adversary доказательство не доказывает безопасность против mobile attacker, который накапливает секреты разных составов за 50 часов. Proactive transfer — нужный механизм, но граница его применимости требует отдельного доказательства.

## Полный uint256 и точный aggregate

`10^9·(2^256−1) < 2^286`. Один masked scalar можно проектировать в кольце с 288 битами; это **36 байт полезной masked-части**, не весь report. Другой вариант — четыре 64-битных limbs, каждый суммируется как минимум в 94 битах, затем восстанавливается общее число. Выбор кодировки должен быть связан proof с исходным uint256.

Нельзя использовать существующий uint32 accumulator и просто разрешить входу 256 бит: сначала меняются PRG expansion, представление, арифметика и проверки переполнения. Также нельзя использовать 255-битное поле BLS12-381 как единственное поле для всей 286-битной суммы.

## Проверка реальных исходников Flamingo

Проверен upstream commit `a7bd1be7985a6db9251f4b5ac3ac23048a14781f` через GitHub API и raw source. Это учебный прототип; обнаруженное ниже относится к этому коду, а не опровергает формальную конструкцию статьи.

- `util/param.py`: `vector_type='uint32'`, vector length 16000. `-e 1` означает один uint32, не uint256. [Параметры](https://github.com/eniac/flamingo/blob/a7bd1be7985a6db9251f4b5ac3ac23048a14781f/util/param.py).
- `SA_ClientAgent.py`: входом служит `np.ones`; PRG выдаёт четыре байта на компонент. Report содержит NumPy vector, serialized self-share ciphertexts и pairwise ciphertexts. AES-GCM tag от `encrypt_and_digest` отбрасывается; расшифрование не проверяет tag. PRF-результат перед hash-to-curve обрезан `& 0xFFFF`, оставляя только 65536 кандидатов pairwise seed. Такой код нельзя считать подтверждением production privacy. [Client, строки 232–365 и 428–437](https://github.com/eniac/flamingo/blob/a7bd1be7985a6db9251f4b5ac3ac23048a14781f/agent/flamingo/SA_ClientAgent.py#L232).
- `SA_ServiceAgent.initialize` сам разделяет хранящийся у сервера полный `system_sk` и раздаёт shares. Это упрощение benchmark, а не отсутствие секрета у агрегатора. Учёт communication считает vector bytes и два ciphertext payload; полного wire-envelope этим не измерено. [Server, строки 218–223 и 253–277](https://github.com/eniac/flamingo/blob/a7bd1be7985a6db9251f4b5ac3ac23048a14781f/agent/flamingo/SA_ServiceAgent.py#L253).

Сериализатор в этой короткой проверке не получен из-за сетевой ошибки. Поэтому точный authenticated scalar-report в байтах не заявляется. Собственные исходники Lighthouse в рамках ограниченной проверки не получены; исследованы описание и форматы статьи.

## Что передаётся и что измерять

Flamingo report имеет структуру `masked_amount + L·encrypted_self_share + degree·encrypted_pairwise_seed + authentication/IDs`. Для 60 decryptors и десятков соседей главный overhead находится в seeds/shares. Число 36 байт описывает лишь первую часть. Передача незавершённых self-shares на новый состав может масштабироваться с числом накопленных отчётов.

В Lighthouse у клиента также остаётся несколько KEM/encrypted-seed объектов: краткость общения комитета не делает report константным в один scalar. В опубликованном замере 1024 клиента, 60 decryptors и вектор 16K×32 бит дают **70,76 KB/client**, **68,40 KB server send** с Groth16 и **0,14 KB/decryptor**. Scalar-case, переносы и proof Tribute там не измерены. [Lighthouse, §6, таблица 3](https://www.usenix.org/system/files/usenixsecurity26-garg-sanjam.pdf).

Минимальный следующий эксперимент должен проверить: один проверенный uint256-report → владелец исчез → два изменения комитета → финальный public partition/eligibility → правильная 286-битная сумма → публичная проверка связи → создание закрытого права Nod. Отдельные отрицательные сценарии: конфликтующий digest после handoff, потеря старых транспортных ключей, повтор report, ошибочный input proof, overflow, группа с единственным неизвестным входом. До этого нельзя переносить FL throughput или размеры в обещание миллиарда Tribute за 50 часов.
